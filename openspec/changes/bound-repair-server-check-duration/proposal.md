# Proposal

> **Категория:** надёжность, скорость · **Приоритет:** средний · **Проверка:** воспроизведено на эмуляторе · **Код:** Crown ·
> **Объём:** S–M

## Why

### Находка
Шаг «Доступность серверов» «Починки» делает URL-тест **всех** серверов:

```kotlin
// app/src/simple/java/io/nekohasekai/sagernet/simple/repair/DeviceRepairChecks.kt:378-385
private suspend fun servers(done: Map<RepairStep, StepResult>): StepResult {
    val snapshot = withContext(Dispatchers.IO) { ServerCatalog.load(config.wlKeywords, emptySet(), "") }
    ...
    val rows = urlTest(servers.map { it.id }) ?: return StepResult.skipped(SkipReason.TESTS_BUSY)
```

и весь шаг должен уложиться в 150 с (`simple/repair/RepairEngine.kt:263-268`, `RepairStep.SERVERS -> 150_000L`), включая
ожидание чужой тестовой сессии до 60 с (`BUSY_WAIT_MS`, `DeviceRepairChecks.kt:631`). Движок тестов проверяет профили
пачками по 100 (`bg/test/TestProbe.kt:31`, `:205` `profiles.chunked(batchSize)`), пачки идут одна за другой, внутри пачки —
10 параллельных запросов с таймаутом 3 с (`database/SettingsRegistry.kt:269-270`). Неотвечающий сервер занимает слот 3 с:
сотня таких — около 30 с, 500 — около 150 с.

По истечении срока `runOne` (`RepairEngine.kt:239-242`) возвращает `SkipReason.TIMED_OUT`, тест останавливается, а уже
полученные результаты выбрасываются. Дальше:
- «DNS через VPN» и «Сайты через VPN» тоже помечаются «не проверено: истекло время» (причина передаётся зависимым шагам);
- вердикты «Все серверы недоступны», «Белые списки: нет серверов для них / они не отвечают», «Текущий сервер не отвечает»
  невозможны — им нужен `SERVERS == FAIL/WARN` (`simple/repair/RepairVerdict.kt:85-105`);
- исправление «переключиться на рабочий сервер» не предлагается.

### Влияние
«Починку» запускают, когда ничего не работает, — тогда большая часть серверов как раз не отвечает (белые списки, блокировка
протокола). На подписках из сотен и тысяч серверов «Починка» 2,5 минуты крутит один шаг и заканчивается вердиктом, не
связанным с серверами. На эмуляторе с подпиской из 504 серверов (2 рабочих, 500 неотвечающих) шаг занял 151 с и закончился
таймаутом; итоговый вердикт — «оптимизация батареи», хотя два рабочих сервера были и текущий «Авто» работал.

### Как воспроизвести
Эмулятор Android 17, debug-сборка `0a0fcc4e`, простой интерфейс, журнал уровня info.
1. Подписки на 504 сервера: 2 рабочих локальных + 500 на адресах TEST-NET `192.0.2.0/24` (не отвечают). VPN подключён
   в «Авто», других тестов нет.
2. «Настройки» → «Something not working?» → «Check again».
3. Фактически:
   ```
   05:03:12 simple repair: subscription -> ok
   05:05:43 simple repair: ru_direct -> ok {reached=4, asked=4}
   05:05:43 simple repair: results … servers skipped(timed_out), dns_vpn skipped(timed_out), sites_vpn skipped(timed_out), …
   05:05:43 simple repair: finished, verdict cause battery
   ```
   Шаг «Доступность серверов» — 151 с, «не проверено: истекло время».
4. Для сравнения: с подпиской из 2 серверов тот же шаг занимает секунды и даёт «отвечают 2 из 2».

## What Changes
1. (рекомендуется) Тестировать выборку, достаточную для вывода, а не все серверы: текущий сервер (участники работающей
   сборки текущего селектора), серверы для белых списков (если сеть с белыми списками), и до N остальных (50–100) — лучших по
   последней задержке и по одному на страну. В `ServersSummary` и отчёте указывать, что проверена выборка.
2. Принимать частичный результат: по сроку шага брать уже пришедшие строки `TestSessionClient.state` и делать вывод по ним
   (ответил хоть один → проверки через VPN возможны; «ни один из проверенных N»).
3. Для «Починки» сократить таймаут одного сервера (1,5–2 с) и поднять параллельность: вопрос шага — отвечает ли хоть что-то.
   Остановить тест, как только найден рабочий сервер для проверок через VPN и есть ответ про текущий.

Проверка: тот же сценарий — шаг укладывается в 30–60 с, вердикт не «не удалось определить»/посторонний. Если не ответил ни
один проверенный сервер: при проверке всех серверов — «Все серверы недоступны», при выборке — «Ни один из проверенных
серверов не ответил». Исправления, рассчитанные на отказ всех серверов, по одной выборке не применяются.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `connection-repair` (simple-ui-redesign): «Сервер для проверок через VPN» и «Итоговый вердикт» — шаг доступности серверов
  укладывается в срок на подписках любого размера (выборка и/или частичный результат), и вердикты по серверам доступны.

## Impact
- **Код:** `simple/repair/DeviceRepairChecks.kt` (`servers`, `urlTest`), `simple/repair/RepairEngine.kt` (срок шага и частичный
  результат), `simple/repair/RepairReport.kt` (пометка «выборка»).
- **Upstream:** код Crown; движок тестов не меняется (пункты 1–2). Пункт 3 — параметры теста передаются из Crown, если
  `TestSpec` их принимает; иначе нужен патч upstream — предпочтительнее пункты 1–2.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** выборка может пропустить единственный рабочий сервер — поэтому текущий селектор и серверы для белых списков
  проверяются всегда. Связано: `make-repair-aware-of-background-tests` (ложный «никто не отвечает» при фоновой сессии),
  `limit-automatic-server-tests` (те же полные прогоны в разделе «Серверы»).
- **Проверка исправления:** сценарий выше с 500 и 2000 серверами; время шага и вердикт до/после.
