# Proposal

> **Категория:** скорость, стабильность · **Приоритет:** низкий · **Проверка:** подтверждено по коду ·
> **Код:** upstream · **Объём:** S–M

## Why

### Находка
Разбор импорта и подписок в целом линейный, но в четырёх местах работа растёт квадратично от размера недоверенного
текста, а длина строки, ссылки и поля не ограничена (есть только общие пределы: тело подписки 64 МиБ, файл 50 МиБ).

1. **Поиск парной скобки с каждой строки.** Если документ не разобрался как целый JSON, `document()` передаёт его в
   `documentBody()` и далее в `Scan.forEachItem`
   (`app/src/main/java/io/nekohasekai/sagernet/outbound/import/ProfileImport.kt:426-444`, `:470-474`). Для каждой строки,
   которая начинается с `{` или `[`, парная скобка ищется до конца **всего** текста:
   ```kotlin
   // ProfileImport.kt:1280-1286
   if (s[idx] == '{' || s[idx] == '[') {
       val end = matchingClose(s, idx)   // :1232-1254, идёт до s.length, если пары нет
       if (end >= 0) { ... continue }
   }
   ```
   Текст `"{\n"` × 50 000 (100 КБ) — около 2,5·10⁹ шагов `matchingClose`; 1 МБ — около 2,5·10¹¹.
2. **Punycode без предела длины метки.** `Hosts.normalizeName` переводит не-ASCII метку в ACE
   (`outbound/link/Hosts.kt:229-246`), а проверка «≤ 63 символа» (`isValidAsciiLabel`, `:221`, `:248`) стоит **после**
   кодирования. `Punycode.encode` (`Hosts.kt:16-52`) на каждое различное значение кодовой точки дважды проходит весь вход:
   O(n·d). Хост из 20 000 разных иероглифов — около 8·10⁸ операций, а нормализация хоста на одну ссылку выполняется
   несколько раз.
3. **Регулярка числа dnst.** `Dnstt.kt:57` `"[+-]?([0-9]+\\.?[0-9]*|\\.[0-9]+)([eE][+-]?[0-9]+)?"` с `matches()`
   (`parseNumber`, `:67-70`; поле `rps` ссылки `dnst://`, `:414-418`): при пустом `\.?` цифры делятся между `[0-9]+` и
   `[0-9]*`, и на входе «n цифр + `x`» движок с возвратами перебирает O(n²) разбиений. Это вывод из устройства регулярки;
   на ICU-движке Android не замерено.
4. **Повторы в списке доменов маршрута подписки.** `RouteProfile.appendSimpleAddressRule` проверяет повтор линейным
   поиском по `MutableList` (`route/RouteProfile.kt:95`: `if (stored !in values) values.add(stored)`) и вызывается на каждую
   строку маршрута подписки (`group/SubscriptionRoute.kt:238-240`): 50 000 доменов — около 1,25·10⁹ сравнений.

Обновление подписки разбирается в процессе `:bg` в однопоточной очереди `SubscriptionQueue.drain`
(`group/SubscriptionQueue.kt:332-349`), цикл разбора отмену не проверяет. Пока идёт разбор, стоят обновления других
подписок, импорт текста (он ставится в ту же очередь) и действия с группами. В simple тот же разбор запускается для нового
содержимого буфера обмена, когда окно получает фокус (`app/src/simple/java/io/nekohasekai/sagernet/simple/SimpleActivity.kt:433-438`,
`simple/add/AddViewModel.kt:188-204`, на `Dispatchers.IO`).

### Влияние
Обычные подписки этот путь не задевают: в форматированном JSON вложенные объекты идут с отступом, строки JSON Lines
закрываются в пределах строки, реальные маршрутные списки — сотни и тысячи доменов (миллисекунды). Проблема проявляется
на сломанном или враждебном ответе подписки, на мусоре в буфере обмена (веб-страница может записать туда текст) и на
специально собранной ссылке. Тогда — от секунд до часов 100 % одного ядра в процессе VPN (нагрев, батарея), подписки и
импорт не работают, автообновление повторяет это по расписанию. Требование `profile-management` «Subscription update»,
сценарий «Subscription fetch failure» (ошибка показана, профили сохранены), в этом случае не выполняется: нет ни ошибки,
ни конца.

### Как воспроизвести
Шаги выведены из кода и не прогонялись.
1. JVM-тест: `ProfileImport.parse` на `"{\n".repeat(50_000)` — замерить время; ожидается порядок секунд и рост примерно
   в 4 раза при удвоении длины.
2. JVM-тест: ссылка `vless://` с хостом из 20 000 различных иероглифов (с U+4E00) — замер `Hosts.toAceHost` и `parse`.
3. На эмуляторе (регулярки ICU): ссылка `dnst://` в режиме `vaydns`, в поле 44 — 50 000 цифр и `x`; замер `parseNumber`.
4. JVM-тест: маршрут подписки из 50 000 строк `domain:aN.example` — замер `appendSimpleAddressRule` по всем строкам.
5. На устройстве: HTTP-сервер на хосте отдаёт тело из шага 1 (`adb reverse tcp:8099 tcp:8099`), подписка
   `http://127.0.0.1:8099/sub`, «Обновить». Наблюдать `adb shell top -H -p <pid процесса :bg>` — поток очереди на 100 %;
   обновление второй подписки не начинается, пока разбор не закончится.

## What Changes
- Рекомендуется (закрывает весь класс): пределы на входе разбора — длина одного элемента или ссылки (порядка 64 КБ;
  предел сверить с реальными большими экспортами `vpn://`), длина хоста ≤ 253 и метки ≤ 63 кодовых точек **до** Punycode
  (ACE-метка не короче исходной, поэтому длинную можно отвергать сразу). Слишком длинный элемент отбрасывается с отчётом.
- `forEachItem`: таблица пар скобок за один проход со стеком (O(n)), конец элемента берётся из неё; для корректных
  документов поведение не меняется.
- `Dnstt.DECIMAL`: без перекрывающихся кванторов (`[0-9]+(\.[0-9]*)?|\.[0-9]+` с экспонентой) или ручной разбор числа,
  плюс предел длины поля.
- `appendSimpleAddressRule`: проверка повторов через `HashSet` рядом со списком.
- Частичная мера: проверка отмены и срок на разбор в очереди подписок — CPU не сэкономит, но очередь освободится.
- Проверка: тесты из шагов 1–4 укладываются в миллисекунды; существующий корпус тестов импорта даёт тот же результат.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `profile-management`: в «Import and share» и «Subscription update» добавляется — разбор ограничен по длине элемента и
  хоста; слишком длинный ввод отвергается с ошибкой, а не обрабатывается неограниченно долго.

## Impact
- **Код:** `outbound/import/ProfileImport.kt`, `outbound/link/Hosts.kt`, `outbound/types/Dnstt.kt`, `route/RouteProfile.kt`.
- **Upstream:** все файлы — код upstream, ни один не входит в `TOUCH_POINTS`/`FORK_IDENTITY_POINTS`. Нужна новая точка
  правки («пределы разбора недоверенного ввода») или патч в upstream — там тот же недостаток.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** слишком строгий предел длины отвергнет законную большую ссылку; предел лучше ставить на хост и поля, а на
  элемент — с запасом. Таблица пар скобок должна в точности повторять обработку строк и экранирования `matchingClose`.
- **Проверка исправления:** JVM-тесты на время из «Как воспроизвести» и прогон существующих тестов импорта.
- **Внешние источники:**
  - RFC 3492, Punycode (раздел 6.4 — переполнение): https://www.rfc-editor.org/rfc/rfc3492
  - RFC 1035, 2.3.4 (метка ≤ 63 октетов, имя ≤ 255): https://www.rfc-editor.org/rfc/rfc1035
