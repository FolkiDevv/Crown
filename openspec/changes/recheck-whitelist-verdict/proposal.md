# Proposal

> **Категория:** надёжность · **Приоритет:** низкий · **Проверка:** подтверждено по коду (механизм частично наблюдался на
> эмуляторе; сценарии ложного вердикта — гипотеза) · **Код:** Crown · **Объём:** S

## Why

### Находка
1. **Вердикт без подтверждения.** Сеть считается сетью с белыми списками, если ответил хотя бы один разрешённый адрес и ни
   одного запрещённого (`simple/regime/RegimeClassifier.kt:68-75`). Таймаут 4 с (`NetworkProber.kt:56`) считается
   недоступностью. Второй взгляд через 3 с делается только для `inconclusive` (сеть пропала) или `partial` — когда не ответил
   какой-то **разрешённый** адрес (`NetworkProber.kt:106-110`, `NetworkRegimeWatcher.kt:298-307`). Если все разрешённые
   ответили, а все запрещённые не ответили (в том числе по таймауту), вердикт применяется сразу: «Авто» переключает маршрут и
   сервер и перезапускает ядро.
2. **На Wi‑Fi вердикт не пересматривается.** Повтор по таймеру есть только в мобильной сети:
   ```kotlin
   // app/src/simple/java/io/nekohasekai/sagernet/simple/regime/NetworkRegimeWatcher.kt:244-249
   val cellular = SagerNet.connectivity.getNetworkCapabilities(network)
       ?.hasTransport(NetworkCapabilities.TRANSPORT_CELLULAR) == true
   if (cellular) start(owner, network, "15-minute timer, mobile network")
   ```
   Других поводов проверить ту же сеть, кроме выбора «Авто» пользователем и «Починки», нет: `PhysicalNetworkMonitor`
   обрабатывает только `onAvailable`/`onLost` (`PhysicalNetworkMonitor.kt:30-42`); `onCapabilitiesChanged` (сеть прошла
   портал авторизации, получила `VALIDATED`) проверки не вызывает. Результат первой проверки Wi‑Fi действует весь сеанс в этой
   сети.

Оба пункта соответствуют букве traffic-modes («Определение белых списков в сети»; «Моменты проверки» требуют повторов только в
мобильной сети), поэтому это не нарушение спецификации, а недостающая страховка.

Что ограничивает эффект: монитор регистрируется через `registerBestMatchingNetworkCallback` (`PhysicalNetworkMonitor.kt:67`).
Пока Wi‑Fi за порталом не прошёл проверку, а сотовая сеть есть, «лучшей» считается сотовая; когда Wi‑Fi получает `VALIDATED`
и становится лучшей, приходит `onAvailable` — и проверка. Значит, сценарий портала опасен в основном без сотовой сети
(планшет, выключенные данные, роуминг).

### Влияние
Сценарии ложного и стойкого вердикта (на реальных сетях не проверены):
- публичный Wi‑Fi с порталом без сотовой сети: до входа «огороженный сад» пропускает российские сервисы и не пропускает
  остальное → «белые списки»; после входа проверка не повторяется, и до конца сеанса Wi‑Fi «Авто» работает по правилам белых
  списков — через серверы для них (обычно медленные или с лимитом трафика) и их DNS; пользователь видит «Авто · белые списки»
  в обычной сети;
- перегруженная сеть, где зарубежные адреса отвечают дольше 4 с, а российские быстро, — ложные «белые списки» по одной проверке.
Частота — низкая, но вердикт держится до смены сети.

### Как воспроизвести
Наблюдалось на эмуляторе (Android 17, debug `0a0fcc4e`) при имитации белых списков подменой адресов `probes.blocked` в
`files/simple/config.json` на несуществующие имена: каждый вердикт применялся по единственной проверке без второго взгляда —
`check #6 … allowed 4/4, blocked 0/4 reachable in 687 ms -> whitelist` → `whitelist applied (service change: reload)` в ту же
секунду.

Не проверено (нужна реальная сеть или стенд с порталом):
1. «Авто», Wi‑Fi без сотовой сети, на хосте отбросить (DROP) адреса `probes.blocked` → вердикт «белые списки».
2. Снять блокировку, ждать 20–30 мин: строки `15-minute timer` для Wi‑Fi нет, режим «Авто · белые списки» держится до смены сети.
3. Для портала — публичный Wi‑Fi или эмулятор с локальным порталом (`captive_portal_*` в `settings global`).

## What Changes
1. (рекомендуется) Перепроверять текущую сеть при смене её возможностей: обработать `onCapabilitiesChanged` в
   `PhysicalNetworkMonitor` и запускать проверку, когда у текущей сети появляется `NET_CAPABILITY_VALIDATED` или пропадает
   `CAPTIVE_PORTAL`. Пока у сети есть `CAPTIVE_PORTAL` (или нет `VALIDATED`), результат «белые списки» не применять.
2. Подтверждать вердикт, меняющий маршрутизацию: второй взгляд через 3 с и тогда, когда все запрещённые адреса не ответили
   по таймауту (расширить существующее условие `partial`).
3. По желанию (требует правки спецификации): редкий повтор на Wi‑Fi, пока действует «Авто · белые списки» (раз в 30–60 мин).

Проверка: шаги 1–2 — после снятия блокировки (или входа в портал) вердикт меняется на «обычная сеть»; ложный вердикт по
таймаутам не применяется без второго взгляда.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `traffic-modes` (simple-ui-redesign): «Моменты проверки белых списков» — проверка также при получении сетью статуса
  «проверена» (после портала); «Определение белых списков в сети» — вердикт по одним таймаутам запрещённых адресов
  подтверждается повторной проверкой.

## Impact
- **Код:** `simple/regime/PhysicalNetworkMonitor.kt`, `simple/regime/NetworkRegimeWatcher.kt`, `simple/regime/NetworkProber.kt`
  (условие второго взгляда).
- **Upstream:** код Crown.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** лишние проверки (трафик, пробуждения) — `VALIDATED` меняется редко; второй взгляд задерживает реакцию на
  настоящие белые списки на 3–8 с. Каждая лишняя смена вердикта — перезапуск ядра (см.
  `debounce-auto-mode-restarts-on-network-change`, `keep-tunnel-during-in-place-restart`).
- **Проверка исправления:** JVM-тест классификатора/условия второго взгляда; сценарий с порталом на реальном Wi‑Fi.
- **Внешние источники:** `ConnectivityManager.registerBestMatchingNetworkCallback` (API 31) и
  `NetworkCallback.onCapabilitiesChanged`, `NetworkCapabilities.NET_CAPABILITY_VALIDATED` / `NET_CAPABILITY_CAPTIVE_PORTAL` —
  developer.android.com, справочник `android.net`.
