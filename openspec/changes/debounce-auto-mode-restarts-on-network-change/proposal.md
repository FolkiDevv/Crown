# Proposal

> **Категория:** надёжность, скорость · **Приоритет:** средний · **Проверка:** воспроизведено на эмуляторе · **Код:** Crown ·
> **Объём:** S–M

## Why

### Находка
В режиме «Авто» наблюдатель сети в `:bg` (`simple/regime/NetworkRegimeWatcher.kt`) реагирует на каждую смену физической
сети сразу и без ограничения частоты, а результат проверки помнит только для одной сети.

1. `onNetwork` (`:208-232`) на каждое `onAvailable`/`onLost` монитора (`PhysicalNetworkMonitor.kt:30-42`) сразу запускает
   проверку; ожидания устоявшейся сети нет.
2. Хранится одна запись «режим@сеть» (`RegimeStore.kt:13-17`, ключ `simple_regime`). Перед каждой проверкой
   `forgetOtherNetwork` (`NetworkRegimeWatcher.kt:345-358`) заменяет результат прежней сети на «ещё не проверено» для новой и,
   если «Авто» шло по белым спискам, тут же переключает маршрут на «Умный»: `applyRegime(RegimeRecord(null, …))` →
   `ServiceChange.RELOAD` → `oweReload` → `SagerNet.reloadService()` (`:425-447`).
3. Через 0,4–2,5 с приходит вердикт новой сети, и если в ней тоже белые списки — второй `RELOAD`.

В `oweReload` нет предела частоты (в отличие от `TrafficModeApplier`, `RESTART_WAIT_MS`), а возврат в сеть, результат которой
был известен секунды назад, снова проходит «Умный» и два перезапуска. Цикла самовозбуждения нет: монитор слушает сеть без VPN,
и перезапуск ядра нового `onAvailable` не порождает.

Требование спецификации соблюдено формально — «“Авто” MUST NOT применять результат, полученный в другой физической сети: до
результата для текущей сети действуют правила умного режима» (traffic-modes «Моменты проверки белых списков»), — но оно не
запрещает помнить результаты недавних сетей и не требует перезапускать ядро ради промежуточного «Умного».

### Влияние
Каждая смена сети в зоне белых списков стоит **двух** перезапусков ядра на месте: обрыв всех соединений и окно, в котором TUN
закрыт и трафик идёт мимо VPN (механизм и решение — `keep-tunnel-during-in-place-restart`). Плюс 1–3 с «Умного» маршрута —
в зоне белых списков это время без связи. На границе зоны (слабый домашний Wi‑Fi, подъезд, офис), где сеть меняется каждые
десятки секунд, VPN перезапускается так же часто: звонки, загрузки и мессенджеры рвутся.

На эмуляторе — 6 смен сети за 2 минуты дали **12 перезапусков** ядра, по два на каждую смену, хотя обе сети имели белые списки
и итоговый маршрут после каждой смены был тем же.

### Как воспроизвести
Эмулятор Android 17, debug-сборка `0a0fcc4e`, простой интерфейс, «Авто», журнал уровня info. Белые списки имитируются для
обеих сетей эмулятора: в сохранённой конфигурации проверок (`files/simple/config.json`, через `run-as`) версия поднята до 999, а
адреса `probes.blocked` заменены на несуществующие имена `https://blocked-a.invalid/` … `-d.invalid/` (разрешённые адреса
оставлены).
1. Подключиться: `check #3 … allowed 4/4, blocked 0/4 reachable in 689 ms -> whitelist`,
   `whitelist applied (service change: reload)`.
2. Трижды выключить и включить Wi‑Fi с интервалом 20 с (`agent-device settings wifi off|on`).
3. Фактически на каждую смену сети (журнал, сокращено):
   ```
   05:14:33 physical network 527391707149, the result of network 583226281997 (whitelist) no longer applies (service change: reload)
   05:14:33 ServiceStopTrace … restart=true state=Connected profileId=4      ← «Умный»
   05:14:33 VpnLifecycleTrace stage=tun-close success
   05:14:35 check #8 on network 527391707149: allowed 4/4, blocked 0/4 reachable in 1897 ms -> whitelist
   05:14:35 ServiceStopTrace … restart=true state=Connected profileId=3      ← снова белые списки
   05:14:35 VpnLifecycleTrace stage=tun-close success
   ```
   Итого 12 строк `ServiceStopTrace … restart=true` на 6 смен. Сотовая сеть каждый раз возвращалась с тем же handle
   (`527391707149`), и её результат, полученный за 20 с до того, каждый раз был забыт. Wi‑Fi после каждого включения получал
   новый handle.

## What Changes
1. (рекомендуется) Помнить результаты нескольких последних физических сетей (например, 4 записи «handle → режим, время»).
   При возврате в сеть, у которой есть результат не старше N минут (например, 30), применять его сразу, а проверку запускать
   для подтверждения. Это закрывает частый случай «Wi‑Fi пропал → сотовая → Wi‑Fi» для сотовой сети, handle которой
   сохраняется. Для Wi‑Fi handle меняется при каждом подключении — там поможет только п. 2 (или ключ по идентификатору сети,
   если он доступен без лишних разрешений).
2. Дебаунс: `forgetOtherNetwork` и проверку выполнять через 2–3 с устойчивой новой сети; если за это время вернулась прежняя —
   ничего не делать. Пока у новой сети нет вердикта, работающий маршрут сохраняется, но не дольше срока одной проверки
   (3–5 с с момента смены сети); если вердикта к этому сроку нет — «Умный». При одинаковом вердикте перезапусков нет вовсе.
   Цена: до 5 с действует маршрут, выбранный по результату другой сети. Это отступление от «MUST NOT применять результат,
   полученный в другой физической сети» принято владельцем спецификации и записывается в требование (см. Capabilities).
   Отклонённый вариант — применять «Умный» сразу после дебаунса, строго по нынешнему требованию: он оставляет два
   перезапуска на каждую смену сети без запомненного вердикта.
3. Предел частоты перезагрузок от наблюдателя (не чаще раза в 10–15 с; лишний запрос объединяется с ожидающим, как
   `pendingReload`). Переход на «Умный» по истечении срока из п. 2 под этот предел не попадает: иначе маршрут другой
   сети действовал бы до 15 с.

Проверка: тот же сценарий, цикл «Wi‑Fi выкл → вкл» — не больше одного перезапуска (0, если итоговый режим не изменился),
промежуточного `profileId` «Умного» нет. Если проверка не уложилась в срок из п. 2, применяется «Умный», а затем
вердикт: в этом случае допустимы два перезапуска. Маршрут прежней сети не действует дольше 5 с после смены сети. В обычной
сети поведение не меняется.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `traffic-modes` (simple-ui-redesign): «Моменты проверки белых списков» и «Результат проверки относится только к своей
  сети» — результат помнится за своей сетью ограниченное время и применяется при возврате в неё; после смены сети прежний
  маршрут может действовать до вердикта новой сети, но не дольше 5 с, после чего применяются правила умного режима.
  Требование «MUST NOT применять результат, полученный в другой физической сети» получает это ограниченное по времени
  исключение.

## Impact
- **Код:** `simple/regime/NetworkRegimeWatcher.kt` (`onNetwork`, `forgetOtherNetwork`, `oweReload`),
  `simple/regime/RegimeStore.kt`/`RegimeRecord.kt` (несколько записей), `simple/modes/TrafficModeApplier.kt` (`applyRegime`).
- **Upstream:** код Crown, точки правки не нужны.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** запомненный вердикт может устареть (оператор включил/выключил белые списки) — смягчается подтверждающей проверкой
  и сроком годности записи. Дебаунс задерживает реакцию на настоящую смену зоны на 2–3 с.
- **Проверка исправления:** сценарий выше (подменённая конфигурация проверок); JVM-тесты `ProbeGate`/`RegimeStore` на
  несколько сетей и срок годности.
