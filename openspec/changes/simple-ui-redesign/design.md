# Design

## Context

Мотивация и объём — в proposal.md, требования — в `specs/`. Здесь только то, что определяет способ реализации.

- Приложение на View + Material Components 1.8: одна `MainActivity` с боковым меню (`res/menu/main_drawer_menu.xml`) и фрагментами, профили (`*SettingsActivity`) на PreferenceFragment. Kotlin 2.0.21, AGP 8.8.1, KSP 2.0.21-1.0.27, `compileSdk`/`targetSdk` 35, `minSdk` 24.
- Сервис VPN работает в процессе `:bg` (`bg/BaseService`, `bg/VpnService`); интерфейс получает состояние через AIDL (`bg/SagerConnection.Callback.stateChanged`). Запуск, перезагрузка и остановка — `SagerNet.startService()/reloadService()/stopService()`.
- Профили, группы и подписки — Room (`SagerDatabase`, `ProfileManager`, `GroupRepo`); сведения о подписке — `database/SubUserInfo` (трафик, `expire`). Настройки — `DataStore` (key-value в Room, общий для процессов): `selectedProxy`, `currentRouteId`, `directDns`, `remoteDns`, `netUseProxy`, `vpn_mtu` и др.
- Авто-селектор (`bg/autoselector`) уже умеет: группы-источники, фильтр по имени (регулярное выражение), уровни (сервер попадает в первый подходящий уровень, используется верхний уровень с рабочим сервером), исключение недоступных.
- Тесты — `bg/test/TestEngine` через `ICoreService.startTest(TestSpec)`: URL-test, IP/страна выхода (`IpTestRunner`, `widget/ExitIp`), service check, скорость.
- Маршрутные профили: `RouteManager`, `RouteRepo` (снимок `throneproj/routeprofiles`: вшит в ассеты, обновляется через зеркало rule-set, `RouteRepo.bundles()`), `group/RemoteRouteUpdater`. Набор `Profile_Russia` содержит запись `Bypass_Russia` («Bypass Russia»). Маршрутный профиль может нести собственный DNS (`RouteProfile.activeDns()` при `custom_dns`) и условия `network_type`/`wifi_ssid`.
- Импорт: `ui/SubscribeFlows.importText/importUri`, `ui/profile/ProfileTextImport`; журналы: `moe/matsuri/nb4a/utils/LogRedactor` (вырезает URL, секреты, UUID, ключи, публичные IP, а с `hideDestinations` — и домены).
- Правила репозитория (`openspec/config.yaml`, `repository-governance`): локально не собираем Android/Go — сборка и проверка только в CI (`.github/workflows/ci.yml`, job `build`: `app:testOssDebugUnitTest app:assembleOssDebug`) и на устройстве владельца; работа батчами с проверкой после каждого; Python-утилиты только в `tools/diagnostics/` через `uv run`.
- В репозитории сейчас нет remote `upstream`; изменения upstream будут подтягиваться из `throneproj/ThroneForAndroid`.

## Goals / Non-Goals

**Goals:**
- Новый интерфейс как отдельный слой над существующими API, без изменения поведения классического интерфейса и сервиса, кроме перечисленных точек подключения.
- Минимальная площадь конфликтов при слиянии с upstream.
- Максимальное переиспользование: авто-селектор, тесты, RouteRepo, импорт, LogRedactor, экраны классического интерфейса для расширенного режима.
- Чистая логика (классификация сети, ключевые слова, страна по имени, вердикты «Починки», разбор конфигурации) — в классах без Android-зависимостей с JVM unit-тестами в CI.

**Non-Goals:**
- Перевод классических экранов на Compose и редизайн экранов профилей и маршрутов.
- Изменения ядра, протоколов, формата резервных копий, схемы Room.
- Переводы нового интерфейса на языки, кроме английского и русского.
- Автоматические UI-тесты на эмуляторе (в CI нет эмулятора; UI проверяется на устройстве владельца).

## Decisions

### D1. Jetpack Compose + Material 3 с адаптивными компонентами
Новый интерфейс пишется на Compose: `NavigationSuiteScaffold` (нижняя панель / rail по классу ширины), `ListDetailPaneScaffold` (главная и серверы рядом на широком экране), `ModalBottomSheet`, `ListItem`, `FilterChip`, `PullToRefreshBox`, `Switch`. Зависимости: плагин `org.jetbrains.kotlin.plugin.compose` 2.0.21, Compose BOM `2025.05.01` (Material 3 1.3.x), `material3-adaptive-navigation-suite`, `androidx.compose.material3.adaptive:adaptive-layout`/`adaptive-navigation` 1.1.0, `activity-compose` 1.10.1 (совпадает с текущей `activity-ktx`), `lifecycle-viewmodel-compose`/`lifecycle-runtime-compose` 2.8.x. Навигация внутри — простой стек экранов на `rememberSaveable` без navigation-compose (нет нужды в kotlinx.serialization).
- Совместимость с Kotlin 2.0.21 и `compileSdk 35` проверяется в CI первым же батчем; запасной вариант — BOM `2024.12.01`.
- Альтернатива: остаться на View и обновить Material Components до M3. Отклонено: адаптивную навигацию и двухпанельную раскладку для телефона/планшета/ТВ пришлось бы писать и поддерживать самим.

### D2. Изоляция от upstream через source set `app/src/simple/`
Весь новый код — в `app/src/simple/java/io/nekohasekai/sagernet/simple/**`, ресурсы — в `app/src/simple/res/` (с префиксом `simple_` у имён, чтобы исключить коллизии), ассеты — в `app/src/simple/assets/simple/`. Каталоги подключаются к `main` через `android.sourceSets["main"].java/res/assets.srcDir(...)`. Перечень допустимых правок файлов upstream (接入点清单, на него ссылается `repository-governance`):

| # | Файл | Правка |
|---|---|---|
| 1 | `build.gradle.kts` | объявление плагина `org.jetbrains.kotlin.plugin.compose` 2.0.21 (`apply false`) |
| 2 | `app/build.gradle.kts` | применение плагина, `buildFeatures.compose`, зависимости Compose, три `srcDir` |
| 3 | `app/src/main/AndroidManifest.xml` | объявление `simple.SimpleActivity` (фильтры лаунчера остаются на `MainActivity`) |
| 4 | `app/src/main/res/menu/main_drawer_menu.xml` | пункт «Новый интерфейс» (заголовок — строка из `strings_simple.xml`) |
| 5 | `app/src/main/java/io/nekohasekai/sagernet/ui/MainActivity.kt` | в начале `onCreate` — `if (SimpleUi.redirect(this)) return`; обработчик пункта меню — `SimpleUi.switchTo(this, simple = true)` |
| 6 | `app/src/main/java/io/nekohasekai/sagernet/bg/BaseService.kt` | вызовы `SimpleHooks.onServiceStarted/onServiceStopped` (запуск и остановка наблюдателя сети) |
| 7 | `app/src/main/java/io/nekohasekai/sagernet/group/RemoteRouteUpdater.kt` (или место вызова `RouteRepo.refresh()`) | вызов `SimpleConfigRepo.refresh()` рядом с обновлением снимка маршрутов |

Скрипт `tools/diagnostics/upstream_touch_points.py` сравнивает рабочее дерево с `--base` (по умолчанию `upstream/main`) и падает, если изменён файл вне этого списка и вне `app/src/simple/`, `openspec/`, `tools/diagnostics/`; в `app/src/test/` разрешены только новые файлы (JVM unit-тесты нового кода) — изменение файла, который уже есть в `--base` (сейчас там 4 теста upstream), считается правкой вне списка.
- Альтернатива: отдельный Gradle-модуль. Отклонено: новому коду нужен прямой доступ к классам `app` (DataStore, ProfileManager, AIDL), а вынос этих классов в библиотеку переломал бы upstream-структуру.

### D3. Выбор интерфейса и точка входа
Точкой входа остаётся `MainActivity` (лаунчер, `LEANBACK_LAUNCHER`, уведомление, плитка, ярлыки уже ведут в неё). В начале `onCreate`, до `setContentView`, `SimpleUi.redirect(this)` читает выбор из собственных `SharedPreferences("simple_ui")`; если выбран новый интерфейс и `Intent` не несёт действия, которое умеет только классика (например, `QS_TILE_PREFERENCES` или явный флаг «открыть классику»), он запускает `SimpleActivity` с тем же `Intent`-содержимым и завершает `MainActivity`. Так все входы одинаково ведут в выбранный интерфейс без переноса фильтров манифеста. Флаг хранится вне `DataStore`/Room — никаких конфликтов схемы и ключей с upstream. Правило хранения: в `SharedPreferences("simple_ui")` лежат только флаги, которые читает исключительно UI-процесс (выбор интерфейса, однократная подсказка); всё, что читает или пишет процесс `:bg` (режим трафика, списки приложений, id управляемых профилей, результат проверки сети), хранится в ключах `DataStore` с префиксом `simple_` — это key-value в Room, уже работающий между процессами, без изменения схемы. Признак «обновление, а не новая установка» для однократной подсказки определяется как в `FirstStartPrompts` (`lastUpdateTime > firstInstallTime` и отсутствие флага). Переходы из расширенного режима в экраны классики открывают их с флагом «открыть классику», чтобы не сработала переадресация.
- Альтернатива: отдельная активити-«стрелочник» с фильтрами лаунчера. Отклонено: уведомление, плитка и ярлыки upstream по-прежнему открывали бы `MainActivity` напрямую, и пользователь нового интерфейса попадал бы в классику.

### D4. Доступ к данным и состоянию
Экраны работают через ViewModel поверх существующих API: состояние сервиса — `SagerConnection` (тот же AIDL, что у классики); профили/группы — `ProfileManager`/`GroupRepo` + их слушатели, обёрнутые в `Flow`; подписка — `SubUserInfo`; настройки — `DataStore`. Импорт — `SubscribeFlows`/`ProfileTextImport` с адаптером, подавляющим классические диалоги выбора там, где формат однозначен. Файл обрабатывается так же, как в классике (`MainActivity.openFile`): сначала `BackupEntry.open` (распознаёт резервную копию и ведёт в штатное восстановление), и только если это не резервная копия — `SubscribeFlows.importUri`. Экраны расширенного режима — `Intent` на существующие активити/фрагменты классики.

### D5. Режимы трафика как управляемые профили
Режимы не вводят новой логики маршрутизации, а выбирают заранее созданные «управляемые» сущности (их id хранятся в ключах `DataStore` `simple_managed_*`, режим — в `simple_mode`):
- **Умный** — маршрутный профиль, импортированный неинтерактивно из записи `Bypass_Russia` снимка `RouteRepo` (обновляется штатным `RemoteRouteUpdater`).
- **Белые списки** — локально сгенерированный маршрутный профиль: `hijack-dns`, частные сети → direct, всё остальное → proxy; собственный DNS профиля: удалённый DNS через туннель, прямой DNS (для разрешения адресов серверов) — DNS из белого списка из конфигурации. Глобальные настройки DNS пользователя не трогаются.
- **Только выбранные приложения** — штатный per-app режим (список приложений через существующий экран `AppManagerActivity`) + маршрутный профиль умного режима.
- **Per-app область**: в `DataStore` один список (`individual`) с флагами `proxyApps`/`bypass`, поэтому упрощённый интерфейс хранит два своих списка в ключах `DataStore` `simple_apps_selected` (для режима «Только выбранные приложения») и `simple_apps_bypass` (настройка «Приложения без VPN») и оба никогда не очищает; оба процесса читают их одинаково. `TrafficModeApplier` при каждом применении записывает в `DataStore` активную область: для «Только выбранные приложения» — `proxyApps=true`, `bypass=false`, `individual`=выбранные; для остальных режимов — `proxyApps=true`, `bypass=true`, `individual`=«приложения без VPN», а если этот список пуст — `proxyApps=false`. Так выбор из режима приложений не остаётся активным в других режимах, а при возврате к нему восстанавливается.
- **Пустой список выбранных приложений**: при `bypass=false` и пустом `individual` TUN не получает ни одного разрешённого приложения, и Android пропустил бы через VPN все приложения. Поэтому режим «Только выбранные приложения» нельзя выбрать, пока список пуст (пункт ведёт сначала в выбор приложений), а если список опустел, пока режим активен (в том числе после правки в `AppManagerActivity`, откуда изменения считываются обратно в `simple_apps_selected` при возврате), `TrafficModeApplier` переключает режим на «Авто» и сообщает об этом на экране настроек. Пустой список никогда не применяется как include-список.
- **Автовыбор сервера** — два управляемых авто-селектора: «Авто» (все группы; первый уровень — серверы, чьё имя не совпадает с регулярным выражением ключевых слов, серверы для белых списков — последним уровнем, то есть только как запасной вариант, когда обычных рабочих нет) и «Авто · белые списки» (все группы, первый уровень — регулярное выражение ключевых слов, остальные — последним уровнем). Состав групп синхронизируется при добавлении/удалении групп.
- **Применение**: `TrafficModeApplier` выставляет `currentRouteId`, per-app область и, если пользователь выбрал «Авто», `selectedProxy` нужного авто-селектора. Если per-app область изменилась, сервис перезапускается целиком (TUN пересоздаётся с новым списком приложений), иначе — `SagerNet.reloadService()`. Ручной выбор сервера не трогается (требование «Ручной выбор сервера сохраняется»).
- **Подписки через туннель**: в упрощённом интерфейсе `netUseProxy` включается по умолчанию (действует только при поднятом сервисе); в батче 3 проверяется, что семантика ключа именно такая.
- Альтернатива: одно правило по `network_type=cellular`. Отклонено: белые списки не совпадают с типом сети и меняются во времени.

### D6. Наблюдатель сети и проверка белых списков
`NetworkRegimeWatcher` живёт в процессе `:bg` и запускается/останавливается вызовами из `BaseService` (точка 6). Физическую сеть он берёт из уже существующего механизма: подписывается на `DefaultNetworkListener` под собственным ключом (тем же источником `BaseService` заполняет `SagerNet.underlyingNetwork`) — сеть по умолчанию с точки зрения приложения при поднятом VPN может быть самим VPN, поэтому с ней не сравниваем. Плюс таймер 15 минут для мобильной сети. Запросы проверки идут через эту физическую сеть: `network.openConnection()` (HTTPS `HEAD`, таймаут 4 с, параллельно, без cookies и с нейтральным User-Agent). Классификатор (`RegimeClassifier`, чистый Kotlin): ≥1 разрешённый доступен и 0 неразрешённых → белые списки; ничего не доступно → нет интернета (режим не меняется); иначе → обычная сеть. Проверки выполняются строго по одной: каждая получает номер поколения и `Network`, на которой запущена; новый повод для проверки (смена физической сети, таймер, подключение, «Починка») отменяет текущую и запускает следующую с новым номером. Результат записывается, только если его номер — последний выданный и его `Network` совпадает с текущей физической сетью (`SagerNet.underlyingNetwork`); иначе он отбрасывается. Результат пишется в `DataStore` (ключ `simple_regime`) — его видит UI-процесс; при смене результата в режиме «Авто» вызывается `TrafficModeApplier` (в `:bg` — через тот же путь, что и `reloadService`). Проверка из «Починки» использует тот же классификатор.

### D7. Конфигурация проверок через механизм RouteRepo
Файл `simple/config.json` (`version`, `probes.allowed[]`, `probes.blocked[]`, `whitelistDns[]`, `wlKeywords[]`, `timeHosts[]`) вшит в `app/src/simple/assets/simple/`. `SimpleConfigRepo` повторяет модель `RouteRepo`: загрузка через то же зеркало rule-set, копия в `filesDir/simple/`, более новая по `version` побеждает вшитую, неполная или повреждённая отклоняется. Обновление вызывается рядом с обновлением маршрутных профилей (точка 7) и с тем же интервалом. Источник — `config.json` в этом репозитории (raw-URL ветки по умолчанию), чтобы владелец форка мог обновлять списки без выпуска приложения.

### D8. «Починка»
`RepairEngine` (UI-процесс, корутины) выполняет 11 шагов из спецификации как последовательность `RepairStep` с зависимостями; каждый шаг возвращает `ok / warn / fail / skipped(причина) / fixed(что сделано, как откатить)`. Источники проверок:
- интернет без VPN, белые списки, время (заголовок `Date` HTTPS-ответа доверенного хоста), DNS напрямую — через физическую сеть (код D6);
- частный DNS — `LinkProperties.isPrivateDnsActive/privateDnsServerName` (API 28+, на более старых — пропуск); другое VPN — только по сети с `TRANSPORT_VPN` среди активных сетей при выключенном нашем сервисе; `VpnService.prepare() != null` означает лишь, что нет согласия пользователя на VPN (например, после новой установки), и как признак чужого VPN не используется. Если обнаружено чужое VPN, «Починка» не поднимает свой VPN (иначе система отзовёт разрешение у другого приложения), а проверки «DNS через VPN» и «Сайты через VPN» помечаются «не проверено: активно VPN другого приложения»;
- подписка — `SubUserInfo` + время последнего обновления; серверы — `TestEngine` URL-test по всем профилям; шаг «Серверы» выполняется до шагов через VPN и выбирает для них сервер: текущий, если он отвечает, иначе лучший отвечающий (с учётом режима: при белых списках — сначала серверы для белых списков); DNS через VPN и сайты через VPN — service check с `testCurrent`, при выключенном VPN сервис поднимается на сервере, выбранном шагом «Серверы»; российские сайты напрямую — физическая сеть; фон — `BatteryOptimizations.isIgnoring`.
- вердикт по белым спискам различает два случая: в подписке нет ни одного сервера, распознанного как сервер для белых списков → «в подписке нет серверов для белых списков»; такие серверы есть, но не отвечают → «серверы для белых списков сейчас не отвечают».

Автоисправления — только перечисленные в спецификации; каждое регистрирует действие отката, откат выполняется при неуспехе повторной проверки и при остановке. `RepairVerdict` (чистый Kotlin) сводит результаты в один из трёх итогов по таблице известных причин. Отчёт: `report.json` и `report.txt` (шаги, исправления, тайминги), журнал ядра (тот же источник, что у экспорта журнала), итоговая конфигурация, сведения об устройстве — всё через `LogRedactor(hideDestinations = true)` и затем через дополнительный проход `ReportRedactor` только для отчёта: замена на метки (`<server-1>`, …) всех адресов и доменов серверов, известных из профилей пользователя, хостов в любых URL (`LogRedactor.redact` хост в URL сохраняет) и ссылок подписок. Классический экспорт журнала не меняется (вне объёма этого изменения); zip в `cacheDir`, отдача через существующий FileProvider (`res/xml/cache_paths.xml`) и `ACTION_SEND`.

### D9. Строки и языки
Все тексты нового интерфейса — в `app/src/simple/res/values/strings_simple.xml` (английский) и `values-ru/strings_simple.xml`. `tools/diagnostics/i18n_coverage.py` получает второй корень ресурсов `app/src/simple/res` с правилом «только ru». Классические `strings.xml` не меняются совсем: заголовок пункта меню «Новый интерфейс» (точка 4) берётся из `strings_simple.xml` — ресурсы source set'ов объединяются при сборке, а в классике на языках кроме русского этот пункт будет на английском.

### D10. Тестирование
JVM unit-тесты (выполняются в CI `app:testOssDebugUnitTest`): `RegimeClassifier`, построитель регулярных выражений ключевых слов (экранирование, регистр, кириллица), `CountryFromName`, `SimpleConfig` парсер/валидатор, `RepairVerdict`, таблица шагов «Починки» и их зависимостей. UI и сетевые сценарии — проверка на устройстве владельца по чек-листу каждого батча.

## Risks / Trade-offs

- [Compose-зависимости несовместимы с Kotlin 2.0.21 / AGP 8.8.1] → проверка в CI в батче 1; запасной BOM `2024.12.01`; обновление Kotlin не делаем без отдельного решения.
- [Рост размера APK] → R8 уже включён для release; размер фиксируется в батче 1 и сравнивается с текущим релизом.
- [Ложное «белые списки», если заблокированы отдельные зарубежные сайты] → неразрешённые адреса берутся с разных CDN/AS, требуется недоступность всех; повтор через 15 минут; список обновляется удалённо.
- [Ключевые слова ошибочно относят сервер к белым спискам, а изменить нельзя] → консервативный список, обновляемый без релиза; это осознанное решение владельца.
- [Кратковременный разрыв при перезагрузке ядра при смене режима] → смена происходит в основном при смене сети, когда соединения и так рвутся.
- [Конфликты при слиянии upstream в точках 1–7] → правки по 1–10 строк в стабильных местах; скрипт контроля точек; регулярные слияния.
- [Межпроцессное состояние `:bg` ↔ UI] → только через `DataStore` и AIDL, уже работающие межпроцессно.
- [Android TV: фокус и D-pad в Compose] → отдельный батч с проверкой на ТВ.
- [Мелькание классического экрана при переадресации из `MainActivity`] → переадресация выполняется до `setContentView`, без анимации перехода; проверяется на устройстве в батче 1 для лаунчера, уведомления и ТВ.

## Migration Plan

- Выпуск: новый интерфейс по умолчанию для новых и обновлённых установок; однократная подсказка о возврате.
- Откат для пользователя: пункт «Классический интерфейс».
- Откат в коде: каждый батч — отдельный коммит, откатывается независимо; полный откат — удалить вызов `SimpleUi.redirect` в `MainActivity` (точка 5).
