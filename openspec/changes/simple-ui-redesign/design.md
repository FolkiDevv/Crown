# Design

## Context

Мотивация и объём — в proposal.md, требования — в `specs/`. Здесь только то, что определяет способ реализации.

- Приложение на View + Material Components 1.8: одна `MainActivity` с боковым меню (`res/menu/main_drawer_menu.xml`) и фрагментами, профили (`*SettingsActivity`) на PreferenceFragment. Kotlin 2.0.21, AGP 8.8.1, KSP 2.0.21-1.0.27, `compileSdk`/`targetSdk` 35, `minSdk` 24.
- Сервис VPN работает в процессе `:bg` (`bg/BaseService`, `bg/VpnService`); интерфейс получает состояние через AIDL (`bg/SagerConnection.Callback.stateChanged`). Запуск, перезагрузка и остановка — `SagerNet.startService()/reloadService()/stopService()`.
- Профили, группы и подписки — Room (`SagerDatabase`, `ProfileManager`, `GroupRepo`); сведения о подписке — `database/SubUserInfo` (трафик, `expire`). Настройки — `DataStore` (key-value в Room, общий для процессов): `selectedProxy`, `currentRouteId`, `directDns`, `remoteDns`, `netUseProxy`, `vpn_mtu` и др.
- Авто-селектор (`bg/autoselector`) уже умеет: группы-источники, фильтр по имени (регулярное выражение), уровни (сервер попадает в первый подходящий уровень, используется верхний уровень с рабочим сервером), исключение недоступных.
- Тесты — `bg/test/TestEngine` через `ICoreService.startTest(TestSpec)`: URL-test, IP/страна выхода (`IpTestRunner`, `widget/ExitIp`), service check, скорость.
- Маршрутные профили: `RouteManager`, `RouteRepo` (снимок `throneproj/routeprofiles`: вшит в ассеты, обновляется через зеркало rule-set, `RouteRepo.bundles()`), `group/RemoteRouteUpdater`. Набор `Profile_Russia` содержит запись `Bypass_Russia` («Bypass Russia»). Маршрутный профиль может нести собственный DNS (`RouteProfile.activeDns()` при `custom_dns`) и условия `network_type`/`wifi_ssid`.
- Импорт: `ui/SubscribeFlows.importText/importUri`, `ui/profile/ProfileTextImport`; журналы: `moe/matsuri/nb4a/utils/LogRedactor` (вырезает URL, секреты, UUID, ключи, публичные IP, а с `hideDestinations` — и домены).
- Правила репозитория (`openspec/config.yaml`, `repository-governance`): локально не собираем Android/Go — сборка и проверка только в CI (`.github/workflows/ci.yml`, job `build`: `app:testOssDebugUnitTest app:assembleOssDebug`) и на устройстве владельца; работа батчами с проверкой после каждого; Python-утилиты только в `tools/diagnostics/` через `uv run`.
- В репозитории сейчас нет remote `upstream`; изменения upstream будут подтягиваться из `throneproj/ThroneForAndroid`.

## Goals / Non-Goals

**Goals:**
- Новый интерфейс как отдельный слой над существующими API, без изменения поведения классического интерфейса и сервиса, кроме перечисленных точек подключения.
- Минимальная площадь конфликтов при слиянии с upstream.
- Максимальное переиспользование: авто-селектор, тесты, RouteRepo, импорт, LogRedactor, экраны классического интерфейса для расширенного режима.
- Чистая логика (классификация сети, ключевые слова, страна по имени, вердикты «Починки», разбор конфигурации) — в классах без Android-зависимостей с JVM unit-тестами в CI.

**Non-Goals:**
- Перевод классических экранов на Compose и редизайн экранов профилей и маршрутов.
- Изменения ядра, протоколов, формата резервных копий, схемы Room.
- Переводы нового интерфейса на языки, кроме английского и русского.
- Автоматические UI-тесты на эмуляторе (в CI нет эмулятора; UI проверяется на устройстве владельца).

## Decisions

### D1. Jetpack Compose + Material 3 с адаптивными компонентами
Новый интерфейс пишется на Compose: `NavigationSuiteScaffold` (нижняя панель / rail по классу ширины), `ListDetailPaneScaffold` (главная и серверы рядом на широком экране), `ModalBottomSheet`, `ListItem`, `FilterChip`, `PullToRefreshBox`, `Switch`. Зависимости: плагин `org.jetbrains.kotlin.plugin.compose` 2.0.21, Compose BOM `2025.05.01` (Material 3 1.3.x), `material3-adaptive-navigation-suite`, `androidx.compose.material3.adaptive:adaptive-layout`/`adaptive-navigation` 1.1.0, `activity-compose` 1.10.1 (совпадает с текущей `activity-ktx`), `lifecycle-viewmodel-compose`/`lifecycle-runtime-compose` 2.8.x. Навигация внутри — простой стек экранов на `rememberSaveable` без navigation-compose (нет нужды в kotlinx.serialization). Тип навигации выбирается по ширине окна: нижняя панель только при компактной ширине (и в положении «ноутбук» у складных), иначе — боковая панель; умолчание библиотеки оставляет нижнюю панель при компактной высоте, то есть на любом телефоне в альбомной ориентации, что расходится с требованием «Адаптивная навигация». Главная и серверы стоят рядом (`ListDetailPaneScaffold`: главная — панель списка, «Серверы» — панель деталей), когда ширина окна широкая, а высота не компактная: планшет, развёрнутый складной, ТВ (960×540 dp). Телефон в альбомной ориентации тоже бывает шире 840 dp, но при высоте около 400 dp двум панелям не хватило бы места на кнопку и карточки, поэтому он показывает один раздел с кнопкой рядом с карточками (батч 2). Пульт D-pad (батч 11): вокруг элемента в фокусе рисуется кольцо цвета бренда — для строк, кликабельных через модификатор, его даёт `LocalIndication` темы вместе с ripple, для компонентов Material со своим ripple (кнопки, карточки) — модификатор `focusRing`; слой фокуса ripple усилен до 0,2. В режиме ввода с клавиатуры (на ТВ — всегда) открытый раздел или экран отдаёт фокус своему главному элементу (кнопка подключения, «Авто», «Починка», кнопка «назад» у «Починки», основная кнопка диалога), а строки проверок «Починки» и раскрытые подробности принимают фокус, чтобы пульт мог прокрутить к ним текст. `SimpleActivity` наследует `AppCompatActivity`, чтобы язык и ночной режим, выбранные в приложении (`AppCompatDelegate`), действовали и на новый интерфейс на Android ниже 13.
- Совместимость с Kotlin 2.0.21 и `compileSdk 35` проверяется в CI первым же батчем; запасной вариант — BOM `2024.12.01`.
- Альтернатива: остаться на View и обновить Material Components до M3. Отклонено: адаптивную навигацию и двухпанельную раскладку для телефона/планшета/ТВ пришлось бы писать и поддерживать самим.

- Альтернатива: отдельный Gradle-модуль. Отклонено: новому коду нужен прямой доступ к классам `app` (DataStore, ProfileManager, AIDL), а вынос этих классов в библиотеку переломал бы upstream-структуру.

### D3. Выбор интерфейса и точка входа
Точкой входа остаётся `MainActivity` (лаунчер, `LEANBACK_LAUNCHER`, уведомление, плитка, ярлыки уже ведут в неё). В начале `onCreate`, до `setContentView`, `SimpleUi.redirect(this)` читает выбор из собственных `SharedPreferences("simple_ui")`; если выбран новый интерфейс и `Intent` не несёт действия, которое умеет только классика (например, `QS_TILE_PREFERENCES` или явный флаг «открыть классику»), он запускает `SimpleActivity` с тем же `Intent`-содержимым и завершает `MainActivity`. Так все входы одинаково ведут в выбранный интерфейс без переноса фильтров манифеста. Флаг хранится вне `DataStore`/Room — никаких конфликтов схемы и ключей с upstream. Правило хранения: в `SharedPreferences("simple_ui")` лежат только флаги, которые читает исключительно UI-процесс (выбор интерфейса, однократная подсказка); всё, что читает или пишет процесс `:bg` (режим трафика, списки приложений, id управляемых профилей, результат проверки сети), хранится в ключах `DataStore` с префиксом `simple_` — это key-value в Room, уже работающий между процессами, без изменения схемы. Общие с классикой настройки подписок, у которых упрощённому интерфейсу нужно другое умолчание, — «Отправлять HWID» (`sub_send_hwid`) и «Учитывать интервал сервера» (`sub_respect_server_interval`), в классике обе выключены, — `SimpleDefaults` один раз на установку (флаг в `SharedPreferences("simple_ui")`) и до первой загрузки подписки включает, только если ключа в `DataStore` ещё нет (отсутствие строки отличимо от сохранённого «выключено»; у новой установки ключа нет, а признак установки `install_kind` для этого не годится — сборки с упрощённым интерфейсом записывают «fresh» при своём первом запуске, и после обновления он остаётся); сохранённое значение пользователя не меняется. Подписка упрощённого интерфейса не переопределяет интервал сервера у себя (`respectServerInterval` = как в общей настройке), а собственный интервал группы 1440 мин — запасной, когда сервер интервала не сообщает. Отдельного переключателя автообновления у группы нет: без глобального `sub_auto_update` ничего не обновляется, поэтому пока глобальный переключатель ещё не задан (ключа `sub_auto_update` в `DataStore` нет, классическое −30 только подразумевается), упрощённый интерфейс включает его (1440 мин); «выключено», выбранное пользователем (в «Настройках» упрощённого интерфейса или в классике), импорт не меняет, и сводка тогда автообновление не обещает (батч 10), и автоматически начинают обновляться и другие подписки пользователя, у которых не отмечено «пропускать автообновление» (так их и задумывала классика при добавлении). Признак «обновление, а не новая установка» для однократной подсказки определяется как в `FirstStartPrompts` (`lastUpdateTime > firstInstallTime` и отсутствие флага). Переходы из расширенного режима в экраны классики открывают их с флагом «открыть классику», чтобы не сработала переадресация. Экраны классики — фрагменты `MainActivity`, поэтому вместе с флагом передаётся имя экрана (`simple/settings/ClassicVisit`, батч 10), и `SimpleUi.redirect`, когда переадресации нет, отдаёт такой запуск `ClassicVisit` без новых правок `MainActivity`: тот сразу после её `onCreate` (на Android 10+; на старых — при первом `onStart`) показывает экран — список профилей, который `onCreate` уже поставил, заменяется до создания его вида — через её публичные `displayFragmentWithId`/`openSettingsScreen` (подэкраны настроек — DNS, TUN, пресеты, ядро, тестирование, диагностика — открываются поверх корня настроек, как из «Маршрутов») и добавляет в её `OnBackPressedDispatcher` обработчик «назад», который закрывает `MainActivity` и открывает новый интерфейс на «Настройках» вместо перехода на главный экран классики. Новый интерфейс на время перехода закрывается, как при переключении в классику: его окно, оставленное под классикой, ждёт потери фокуса, пока общий главный поток создаёт `MainActivity`, и медленный холодный старт классики (с её запросами первого запуска) приводил к ANR «SimpleActivity не отвечает»; контрольный замер показал, что сам старт у `main` так же долог, но `main` при переключении закрывает новый интерфейс и ANR не даёт. Обработчик добавляется до старта фрагментов, поэтому собственные «назад» экранов классики (вложенные экраны настроек, поиск, выбор) работают как раньше; выход из открытого подэкрана настроек (назад или стрелка) тоже возвращает в новый интерфейс, а не в корень настроек. Боковое меню классики во время такого перехода доступно, и «назад» с любого его экрана тоже ведёт в новый интерфейс; выбор интерфейса не меняется. До батча 4 в классике оставались и `ACTION_VIEW`/`ACTION_SEND` (ссылки, файлы, «Поделиться») и тексты QR-сканера (`EXTRA_IMPORT_TEXTS`); с батча 4 их принимает добавление в новом интерфейсе, а в списке `SimpleUi` остались только `QS_TILE_PREFERENCES`, флаг «открыть классику» и сценарий разрешения Wi-Fi (`EXTRA_WIFI_PERMISSION`, он не относится к импорту). Резервную копию новый интерфейс отдаёт штатному восстановлению: открывает `MainActivity` с `ACTION_VIEW` этого файла и флагом «открыть классику» на том же `Intent` (переадресация его пропускает, а другие запуски не затрагиваются), и `MainActivity` как обычно передаёт файл в `BackupEntry.open` (Tools › Backup). Ссылки маршрутных профилей (`throne://route`, `throne://remoteroute`) новый интерфейс тоже передаёт классике с флагом «открыть классику».
- Альтернатива: отдельная активити-«стрелочник» с фильтрами лаунчера. Отклонено: уведомление, плитка и ярлыки upstream по-прежнему открывали бы `MainActivity` напрямую, и пользователь нового интерфейса попадал бы в классику.

### D4. Доступ к данным и состоянию
Экраны работают через ViewModel поверх существующих API: состояние сервиса — `SagerConnection` (тот же AIDL, что у классики); профили/группы — `ProfileManager`/`GroupRepo` + их слушатели, обёрнутые в `Flow`; подписка — `SubUserInfo`; настройки — `DataStore`. Импорт — `SubscribeFlows`/`ProfileTextImport` с адаптером, подавляющим классические диалоги выбора там, где формат однозначен. Файл обрабатывается так же, как в классике (`MainActivity.openFile`): сначала проверка резервной копии (та же сигнатура «THRN», что у `BackupEntry`; резервная копия уходит в `MainActivity`, где `BackupEntry.open` ведёт в штатное восстановление, см. D3), и только если это не резервная копия — импорт текста файла. Проверка и импорт идут во ViewModel, а загрузка подписки и её завершение (интервал обновления, удаление не загрузившейся группы) — в собственной области корутин импорта, поэтому пересоздание или закрытие экрана их не обрывает. Проверка батча 4 показала, что `SubscribeFlows.importUri` для этого не подходит: текст файла он передаёт в `importText`, а тот для http(s)-ссылки показывает классический выбор из трёх вариантов и импортирует серверы в текущую группу, которой может оказаться подписка (её обновление удалит добавленное). Поэтому файл читается по тем же правилам, что в `SubscribeFlows` (не больше 50 МБ, кодировка по BOM, двоичные данные — не текст), а дальше идёт общим путём автоопределения нового интерфейса (`simple/add/SimpleImport`): одна http(s)-ссылка, `throne://addsub` или `clash://install-config` — подписка (`SubscriptionClient.subscribeUrl`, без диалога), всё, что разбирает `ProfileTextImport`, — серверы в группу «Мои серверы» (первая группа, которая не подписка; `SubscriptionClient.importText`), иначе — сообщение, что это не похоже на ссылку VPN-сервиса. Классические всплывающие отчёты импорта показывает только `MainActivity`, поэтому в новом интерфейсе их нет. Экраны расширенного режима — `Intent` на существующие активити/фрагменты классики.

### D5. Режимы трафика как управляемые профили
Режимы не вводят новой логики маршрутизации, а выбирают заранее созданные «управляемые» сущности (их id хранятся в ключах `DataStore` `simple_managed_*`, режим — в `simple_mode`):
- **Умный** — маршрутный профиль, импортированный неинтерактивно из записи `Bypass_Russia` снимка `RouteRepo` (обновляется штатным `RemoteRouteUpdater`).
- **Белые списки** — локально сгенерированный маршрутный профиль: `hijack-dns`, частные сети → direct, всё остальное → proxy; собственный DNS профиля: удалённый DNS через туннель, прямой DNS (для разрешения адресов серверов) — DNS из белого списка из конфигурации. Глобальные настройки DNS пользователя не трогаются.
- **Только выбранные приложения** — штатный per-app режим (список приложений через существующий экран `AppManagerActivity`) + маршрутный профиль умного режима.
- **Per-app область**: в `DataStore` один список (`individual`) с флагами `proxyApps`/`bypass`, поэтому упрощённый интерфейс хранит два своих списка в ключах `DataStore` `simple_apps_selected` (для режима «Только выбранные приложения») и `simple_apps_bypass` (настройка «Приложения без VPN») и оба никогда не очищает; оба процесса читают их одинаково. `TrafficModeApplier` при каждом применении записывает в `DataStore` активную область: для «Только выбранные приложения» — `proxyApps=true`, `bypass=false`, `individual`=выбранные; для остальных режимов — `proxyApps=true`, `bypass=true`, `individual`=«приложения без VPN», а если этот список пуст — `proxyApps=false`. Так выбор из режима приложений не остаётся активным в других режимах, а при возврате к нему восстанавливается.
- **Пустой список выбранных приложений**: при `bypass=false` и пустом `individual` TUN не получает ни одного разрешённого приложения, и Android пропустил бы через VPN все приложения. Поэтому режим «Только выбранные приложения» нельзя выбрать, пока список пуст (пункт ведёт сначала в выбор приложений), а если список опустел, пока режим активен (в том числе после правки в `AppManagerActivity`, откуда изменения считываются обратно в `simple_apps_selected` при возврате), `TrafficModeApplier` переключает режим на «Авто» и сообщает об этом на экране настроек. Пустой список никогда не применяется как include-список.
- **Автовыбор сервера** — два управляемых авто-селектора: «Авто» (все группы; первый уровень — серверы, чьё имя не совпадает с регулярным выражением ключевых слов, серверы для белых списков — последним уровнем, то есть только как запасной вариант, когда обычных рабочих нет) и «Авто · белые списки» (все группы, первый уровень — регулярное выражение ключевых слов, остальные — последним уровнем). Состав групп синхронизируется при добавлении/удалении групп.
- **Применение**: `TrafficModeApplier` выставляет `currentRouteId`, per-app область и, если пользователь выбрал «Авто», `selectedProxy` нужного авто-селектора. Если per-app область изменилась, сервис перезапускается целиком (TUN пересоздаётся с новым списком приложений), иначе — `SagerNet.reloadService()`. Ручной выбор сервера не трогается (требование «Ручной выбор сервера сохраняется»).
- **Подписки через туннель**: проверка в батче 3 показала, что семантика `netUseProxy` не та: при выключенном сервисе `httpGet` с этим ключом не идёт напрямую, а завершается ошибкой «нет запущенного профиля» (`appRequestsNeedProxy`, `subs_request_proxy_no_profile`), то есть обновление подписок при выключенном VPN перестало бы работать. Поэтому ключ не включается. Вместо этого собственный пакет приложения всегда остаётся в туннеле: в «Только выбранные приложения» он добавляется в include-список, из списка «Приложения без VPN» исключается. Так запросы самого приложения (подписки, маршрутные профили, конфигурация проверок) при включённом VPN идут через туннель по правилам режима — в «Белых списках» через прокси, — а при выключенном VPN напрямую.
- **Полный перезапуск при смене per-app области**: `SagerNet.reloadService()` перезапускает ядро на месте через `stopRunner(restart = true)`, который вызывает `VpnService.killProcesses` — тот закрывает TUN, — и новый старт заново создаёт TUN через `openTun` со списком приложений из конфигурации. Значит, перезагрузка и есть полный перезапуск TUN без остановки сервиса и уведомления; отдельная остановка и запуск не нужны.
- **Когда режим применяется**: при первом открытии упрощённого интерфейса (ключа `simple_mode` ещё нет; классический per-app список переносится в соответствующий список упрощённого интерфейса, include-список с приложениями делает режимом «Только выбранные приложения»), при выборе режима пользователем и после правки любого из двух списков. В остальное время маршрут, выбранный в классическом интерфейсе, не перезаписывается — карточка режима показывает его как «Свои правила». При открытии упрощённого интерфейса include-список без приложений, оставленный незавершённой правкой, сразу заменяется применением режима.
- **Выбор страны в «Серверах»** (батч 5): третий управляемый авто-селектор (ключ `simple_managed_country`, выбор — `simple_country_choice` = «id подписки:ISO-код»). Он один на все выборы: группа — выбранная подписка, фильтр имени — точные имена её серверов этой страны (без серверов для белых списков), стратегия по задержке, поэтому работает лучший отвечающий сервер страны, а при его отказе — следующий. Страна сервера — `CountryFromName` (флаг, название на английском или русском, ISO-код отдельным словом в верхнем регистре; иначе `test_country` проверки IP выхода). После обновления подписки (и при каждом `ensure`) фильтр пересчитывается; если состав изменился, а страна выбрана сейчас, работающий сервис перезагружается. Выбор «Авто» или отдельного сервера сбрасывает выбор страны; режим «Авто» этот селектор не меняет, как любой ручной выбор.
- Альтернатива: одно правило по `network_type=cellular`. Отклонено: белые списки не совпадают с типом сети и меняются во времени.

### D6. Наблюдатель сети и проверка белых списков
`NetworkRegimeWatcher` живёт в процессе `:bg` и запускается/останавливается вызовами из `BaseService` (точка 6). Физическую сеть он получает собственным обратным вызовом `ConnectivityManager` на собственном потоке (`PhysicalNetworkMonitor`) с тем же запросом, что у `DefaultNetworkListener` (INTERNET, NOT_RESTRICTED и по умолчанию NOT_VPN — сеть по умолчанию с точки зрения приложения при поднятом VPN может быть самим VPN, поэтому с ней не сравниваем): слушатели `DefaultNetworkListener` вызываются по очереди на одном потоке, а upstream оставляет там по слушателю на каждую закрытую коробку ядра, и смена сети доходит до конца этой очереди с опозданием в десятки секунд; если система отказывает в регистрации, используется `DefaultNetworkListener` под собственным ключом. Плюс таймер 15 минут для мобильной сети. Запросы проверки идут через эту физическую сеть (`NetworkProber`): клиент OkHttp с `socketFactory` этой сети и собственным `Dns` (`FallbackDns`) отправляет HTTPS `HEAD` ко всем адресам асинхронно (`enqueue`), параллельно; таймауты соединения и чтения 4 с, без прокси, cookies и кэша, редиректы отключены, фиксированный нейтральный User-Agent, при отказе соединения разрешён переход к следующему адресу имени; у каждой проверки свой диспетчер, поэтому отменённая проверка снимается целиком и не занимает потоки следующей; общий предел одного запроса — 8 с. Имена разрешаются DNS этой сети; если он не ответил за 1,5 с, — простыми DNS-серверами из `whitelistDns` конфигурации через ту же сеть (адреса из конфигурации), чтобы сеть со сломанным собственным DNS не считалась сетью без интернета: не больше 4 серверов и 4 с на одно разрешение, записи A — если у сети есть IPv4, AAAA — если есть глобальный IPv6-адрес (обе, если не определить), истёкший вопрос одного семейства не мешает спросить другое; с концом или отменой проверки запросы прекращаются и сокеты закрываются. Если во время проверки сеть пропала (ошибки «сеть недоступна» или у Android больше нет её канала), ответы неполные и ничего не доказывают: такая проверка, как и «белые списки» при недоступном разрешённом адресе, через 3 с повторяется в рамках того же поколения, а неубедительный повтор режим не меняет. Классификатор (`RegimeClassifier`, чистый Kotlin): ≥1 разрешённый доступен и 0 неразрешённых → белые списки; ничего не доступно → нет интернета (режим не меняется); иначе → обычная сеть. Проверки выполняются строго по одной: каждая получает номер поколения и `Network`, на которой запущена; новый повод для проверки (смена физической сети, таймер, подключение, выбор «Авто» пользователем — всё это только пока сервис запущен, так как наблюдатель живёт в `:bg`; при выключенном VPN выбор «Авто» проверку не запускает, она выполнится при подключении; «Починка» запускает собственную проверку тем же классификатором в UI-процессе независимо от VPN) отменяет текущую и запускает следующую с новым номером. Результат записывается, только если его номер — последний выданный и его `Network` совпадает с текущей физической сетью, которую видит наблюдатель; иначе он отбрасывается. Защита от ручной смены режима: каждая ручная смена режима в UI увеличивает счётчик `simple_mode_rev` в `DataStore`; проверка запоминает его значение при старте, а шаг применения в `TrafficModeApplier` под общей блокировкой записи (транзакция Room над key-value `DataStore`) заново читает `simple_mode` и `simple_mode_rev` и применяет результат «Авто», только если режим всё ещё «Авто» и счётчик не изменился. Ручная смена режима применяется тем же `TrafficModeApplier` в той же транзакции, поэтому две записи не перемешиваются, а незавершённые результаты «Авто» после неё становятся недействительными. Результат пишется в `DataStore` (ключ `simple_regime`) вместе с идентификатором физической сети; если сохранённый результат относится не к текущей сети, «Авто» применяет правила умного режима до новой проверки — его видит UI-процесс; при смене результата в режиме «Авто» вызывается `TrafficModeApplier` (в `:bg` — через тот же путь, что и `reloadService`). Проверка из «Починки» использует тот же классификатор.

### D7. Конфигурация проверок через механизм RouteRepo
Файл `simple/config.json` (`version`, `probes.allowed[]`, `probes.blocked[]`, `whitelistDns[]`, `wlKeywords[]`, `timeHosts[]`) вшит в `app/src/simple/assets/simple/`. `SimpleConfigRepo` повторяет модель `RouteRepo`: загрузка через то же зеркало rule-set, копия в `filesDir/simple/`, более новая по `version` побеждает вшитую, неполная или повреждённая отклоняется. Обновление вызывается рядом с обновлением маршрутных профилей (точка 7) и с тем же интервалом. Источник — `config.json` в этом репозитории (raw-URL ветки по умолчанию), чтобы владелец форка мог обновлять списки без выпуска приложения.

### D8. «Починка»
`RepairEngine` (UI-процесс, корутины) выполняет 11 шагов из спецификации как последовательность `RepairStep` с зависимостями; каждый шаг возвращает `ok / warn / fail / skipped(причина) / fixed(что сделано, как откатить)`. Источники проверок:
- интернет без VPN, белые списки, время (заголовок `Date` HTTPS-ответа доверенного хоста), DNS напрямую — через физическую сеть (код D6);
- частный DNS — `LinkProperties.isPrivateDnsActive/privateDnsServerName` (API 28+, на более старых — пропуск); другое VPN — только по сети с `TRANSPORT_VPN` среди активных сетей при выключенном нашем сервисе; `VpnService.prepare() != null` означает лишь, что нет согласия пользователя на VPN (например, после новой установки), и как признак чужого VPN не используется. Если обнаружено чужое VPN, «Починка» не поднимает свой VPN (иначе система отзовёт разрешение у другого приложения), а проверки «DNS через VPN» и «Сайты через VPN» помечаются «не проверено: активно VPN другого приложения»;
- подписка — `SubUserInfo` + время последнего обновления; серверы — `TestEngine` URL-test по всем профилям; шаг «Серверы» выполняется до шагов через VPN и выбирает для них сервер: текущий, если он отвечает, иначе лучший отвечающий (с учётом режима: при белых списках — сначала серверы для белых списков); DNS через VPN и сайты через VPN — service check с `testCurrent`, при выключенном VPN сервис поднимается на сервере, выбранном шагом «Серверы»; российские сайты напрямую — физическая сеть; фон — `BatteryOptimizations.isIgnoring`.
- вердикт по белым спискам различает два случая: в подписке нет ни одного сервера, распознанного как сервер для белых списков → «в подписке нет серверов для белых списков»; такие серверы есть, но не отвечают → «серверы для белых списков сейчас не отвечают».

Автоисправления — только перечисленные в спецификации; каждое регистрирует действие отката, откат выполняется при неуспехе повторной проверки и при остановке. Откатываются только собственные явные записи «Починки» (DNS напрямую, DNS через VPN, MTU, выбранный ею сервер, поднятый ею VPN), каждая — сравнением с записанным значением: значение, изменённое с тех пор кем-то другим, не перезаписывается; для нескольких записей одной настройки старшая ждёт отката младшей; поднятый VPN выключается только в том же сеансе подключения. Обновление подписки и маршрутных профилей — не изменение настройки и не откатывается: полученное от провайдера содержимое и выбор сервера, сделанный самим обновлением (преемник заменённого профиля), остаются; ожидание обновления (очередь `:bg`, запуск преемника) ограничено по времени и нужно только для повторной проверки. `RepairVerdict` (чистый Kotlin) сводит результаты в один из трёх итогов по таблице известных причин. Отчёт: `report.json` и `report.txt` (шаги, исправления, тайминги), журнал ядра (тот же источник, что у экспорта журнала), итоговая конфигурация, сведения об устройстве — всё через `LogRedactor(hideDestinations = true)` и затем через дополнительный проход `ReportRedactor` только для отчёта: замена на метки (`<server-1>`, …) всех адресов и доменов серверов, известных из профилей пользователя, хостов в любых URL (`LogRedactor.redact` хост в URL сохраняет) и ссылок подписок. Классический экспорт журнала не меняется (вне объёма этого изменения); zip в `cacheDir`, отдача через существующий FileProvider (`res/xml/cache_paths.xml`) и `ACTION_SEND`.

### D9. Строки и языки
Все тексты нового интерфейса — в `app/src/simple/res/values/strings_simple.xml` (английский) и `values-ru/strings_simple.xml`. `tools/diagnostics/i18n_coverage.py` получает второй корень ресурсов `app/src/simple/res` с правилом «только ru». Выбор проверяемой части — `--scope all|classic|simple` (по умолчанию `all`); у классических языков есть пробелы перевода, накопленные до этого изменения (54 строки на язык на момент батча 1), поэтому для строк нового интерфейса критерий — `--scope simple` с кодом 0, а `all` показывает и классические пробелы. Классические `strings.xml` не меняются совсем: заголовок пункта меню «Новый интерфейс» (точка 4) берётся из `strings_simple.xml` — ресурсы source set'ов объединяются при сборке, а в классике на языках кроме русского этот пункт будет на английском.

### D10. Тестирование
JVM unit-тесты (выполняются в CI `app:testOssDebugUnitTest`): `RegimeClassifier`, построитель регулярных выражений ключевых слов (экранирование, регистр, кириллица), `CountryFromName`, `SimpleConfig` парсер/валидатор, `RepairVerdict`, таблица шагов «Починки» и их зависимостей. UI и сетевые сценарии — проверка на устройстве владельца по чек-листу каждого батча.

## Risks / Trade-offs

- [Compose-зависимости несовместимы с Kotlin 2.0.21 / AGP 8.8.1] → проверка в CI в батче 1; запасной BOM `2024.12.01`; обновление Kotlin не делаем без отдельного решения.
- [Рост размера APK] → R8 уже включён для release; размер фиксируется в батче 1 и сравнивается с текущим релизом.
- [Ложное «белые списки», если заблокированы отдельные зарубежные сайты] → неразрешённые адреса берутся с разных CDN/AS, требуется недоступность всех; повтор через 15 минут; список обновляется удалённо.
- [Ключевые слова ошибочно относят сервер к белым спискам, а изменить нельзя] → консервативный список, обновляемый без релиза; это осознанное решение владельца.
- [Кратковременный разрыв при перезагрузке ядра при смене режима] → смена происходит в основном при смене сети, когда соединения и так рвутся.
- [Конфликты при слиянии upstream в точках 1–7] → правки по 1–10 строк в стабильных местах; скрипт контроля точек; регулярные слияния.
- [Межпроцессное состояние `:bg` ↔ UI] → только через `DataStore` и AIDL, уже работающие межпроцессно.
- [Android TV: фокус и D-pad в Compose] → отдельный батч с проверкой на ТВ.
- [Мелькание классического экрана при переадресации из `MainActivity`] → переадресация выполняется до `setContentView`, без анимации перехода; проверяется на устройстве в батче 1 для лаунчера, уведомления и ТВ.

## Migration Plan

- Выпуск: новый интерфейс по умолчанию для новых и обновлённых установок; однократная подсказка о возврате.
- Откат для пользователя: пункт «Классический интерфейс».
- Откат в коде: каждый батч — отдельный коммит, откатывается независимо; полный откат — удалить вызов `SimpleUi.redirect` в `MainActivity` (точка 5).
