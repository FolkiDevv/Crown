# Proposal

> **Категория:** надёжность · **Приоритет:** средний · **Проверка:** подтверждено по коду ·
> **Код:** upstream (планировщик), Crown (частичная мера) · **Объём:** M

## Why

### Находка
Автообновление подписок — одна периодическая работа WorkManager. Период — наибольший общий делитель интервалов всех
автообновляемых групп, не меньше 30 минут (`group/SubscriptionScheduler.kt:83-98`); единственное ограничение — наличие
сети (`:118-120`). В simple интервал подписки 1440 минут, поэтому при одной подписке опрос идёт раз в сутки.

Неудачная попытка отодвигает следующую на весь интервал — так сделано по образцу desktop:

```kotlin
// app/src/main/java/io/nekohasekai/sagernet/group/SubscriptionScheduler.kt:74-78
/** autoUpdateDue (GroupUpdater.cpp:519-523): a failed attempt waits the interval too. */
private fun due(group: ProxyGroup, interval: Long): Long {
    val last = maxOf(group.subLastUpdate, attempts[group.id] ?: 0L)
    return if (last <= 0) 0 else last + interval
}
```

Время попытки записывается до постановки в очередь и при любом исходе (`:149-153`), воркер всегда возвращает
`Result.success()` (`:169-176`), `Result.retry()` и backoff не используются, ошибка фонового обновления уходит только в
журнал. Память о попытках живёт в процессе `:bg` (`:49-50`): новый процесс неудачу забывает, но следующий опрос всё равно
наступит только через период. Открытие приложения опрос не приближает: перепланирование с политикой `UPDATE` сохраняет
начало текущего периода (`:34-36`, `:104-107`). simple сам просроченные подписки не обновляет — только по кнопке
(`simple/servers/ServersViewModel.kt:283`, `simple/subs/NoticesViewModel.kt:135`) и в «Починке».

Временные ошибки, из-за которых теряются сутки:
- сеть только что появилась (ограничение «есть сеть» выполнено, но DNS или маршрут не готовы, captive portal) — при
  выходе из Doze это типичный момент запуска заданий;
- панель провайдера блокируется оператором, а в момент опроса VPN выключен: в `:bg` запрос идёт напрямую
  (`ktx/Nets.kt:149-153`) и падает на каждом опросе без VPN;
- кратковременный сбой панели (5xx, 429).

### Влияние
Пользователь, который не открывает приложение, после одной неудачной попытки живёт со старой подпиской ещё сутки, после
двух — двое. Для аудитории Crown это заметно: провайдеры меняют адреса серверов после блокировок, и старые серверы
перестают работать. Сообщения о сроке подписки и лимите трафика, которые проверяются после обновления, приходят с той
же задержкой. Когда VPN выключен и приложение не открывают, система (App Standby Buckets, Doze) ещё и сдвигает
единственную суточную попытку окнами обслуживания.

### Как воспроизвести
Шаги выведены из кода, не прогонялись.
1. simple, одна подписка, автообновление по умолчанию. `adb shell dumpsys jobscheduler | grep -A20 dev.folki.crown.debug`
   — найти задание WorkManager и его id.
2. Заблокировать на хосте адрес панели подписки (сеть эмулятора остаётся «подключённой») и выполнить
   `adb shell cmd jobscheduler run -f dev.folki.crown.debug <id>`.
3. В logcat — строка автообновления группы и ошибка загрузки. Снять блокировку.
4. Фактический результат: до следующего периода (около суток) обновлений нет; `dumpsys jobscheduler` показывает
   следующий запуск через ~24 ч, время последнего обновления группы прежнее.
5. Тест: юнит-тест на `checkAutoUpdate` с подменённой очередью — после неудачной попытки группа считается «не к сроку»
   на весь интервал.

## What Changes
- Рекомендуется: различать временную ошибку (нет сети, таймаут, 5xx, 429) и постоянную (прочие 4xx, пустой ответ, лимит
  устройств). При временной не записывать попытку на весь интервал, а назначить повтор с экспоненциальной задержкой
  (15 мин → 30 → 60 → …, но не позже обычного срока). Технически — отдельная одноразовая работа для упавших групп
  с `setBackoffCriteria(EXPONENTIAL, …)` и `Result.retry()`; периодический опрос остаётся как есть. Для этого очередь
  должна возвращать планировщику исход обновления группы.
- При постоянной ошибке — как сейчас, через интервал (чтобы не тратить батарею и трафик).
- Частичная мера в коде Crown: при подключении VPN (хук запуска сервиса в simple) запускать проверку просроченных групп —
  это закрывает подписки, доступные только через VPN. По желанию — то же при открытии simple, если подписка не
  обновлялась дольше интервала.
- Проверка: сценарий выше — после снятия блокировки подписка обновляется в пределах задержки повтора (не больше часа),
  а не через сутки.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `profile-management`: требование «Subscription update» дополняется — неудачное автоматическое обновление из-за
  временной ошибки повторяется с нарастающей задержкой, не дожидаясь полного интервала.

## Impact
- **Код:** `group/SubscriptionScheduler.kt`, `group/SubscriptionQueue.kt` (исход задачи для планировщика); для частичной
  меры — хуки simple (`app/src/simple/`).
- **Upstream:** `SubscriptionScheduler.kt` и `SubscriptionQueue.kt` не входят в точки правки: нужна новая точка или патч
  в upstream. Это отход от паритета с desktop, его надо отметить в комментарии. Частичная мера — код Crown через
  существующую точку 6 (`BaseService.kt`, хуки запуска сервиса).
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** частые повторы при неверно классифицированной ошибке расходуют батарею и трафик — нужен потолок числа
  повторов. Повтор, совпавший с подключением VPN, конкурирует с ним за тестовый движок (URL-тест после обновления).
- **Проверка исправления:** сценарий 1–4; юнит-тест классификации ошибок и расчёта следующей попытки.
- **Внешние источники:**
  - WorkManager: повтор и backoff (`Result.retry`, `setBackoffCriteria`): https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work#retries_backoff
  - App Standby Buckets: https://developer.android.com/topic/performance/appstandby
