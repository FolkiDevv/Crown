# Proposal

> **Категория:** надёжность · **Приоритет:** низкий · **Проверка:** подтверждено по коду ·
> **Код:** upstream · **Объём:** S

## Why

### Находка
Перезапуск VPN после самообновления устроен так:
1. Перед установкой, если сервис работает, взводится флаг:

   ```kotlin
   // app/src/main/java/io/nekohasekai/sagernet/update/UpdateManager.kt:101
   if (isServiceRunning()) DataStore.resumeAfterUpdate = DataStore.selectedProxy
   ```
2. Установка убивает процессы приложения. Приёмник `PackageReplacedReceiver` в `:bg` получает `MY_PACKAGE_REPLACED`,
   сбрасывает флаг и, если флаг был взведён, запускает VPN — даже при выключенном «Подключаться при запуске»
   (`app/src/main/java/io/nekohasekai/sagernet/BootReceiver.kt:42-51`):

   ```kotlin
   val resume = DataStore.resumeAfterUpdate
   if (resume != 0L) DataStore.resumeAfterUpdate = 0
   val wanted = resume > 0 || DataStore.rememberEnable
   if (wanted && DataStore.selectedProxy > 0 && ...) SagerNet.startService()
   ```

В UI-процессе флаг сбрасывается только в `fail()` (`UpdateManager.kt:130-134`: ошибка загрузки или проверки, отмена в
системном диалоге, отказ установщика). Он остаётся взведённым, если:
- в состоянии «Установка» нажать «Закрыть» (`update/UpdateActivity.kt:135-143` → `UpdateManager.dismiss()`, флаг не
  трогается) — например, когда подтверждение установки ушло в уведомление (`UpdateManager.kt:178-191`, приложение было
  не на переднем плане), а пользователь его не открыл;
- установщик так и не ответил («may never come», `UpdateManager.kt:49`) или процесс умер между записью флага и ответом.

Дальше флаг срабатывает на следующем `MY_PACKAGE_REPLACED` по любой причине. Самый вероятный путь — следующее
встроенное обновление, сделанное при выключенном VPN: строка `:101` при выключенном сервисе флаг не перезаписывает,
поэтому старое значение доживает до установки, и VPN включается сам. То же при ручной установке APK со страницы выпусков.
Сохранённое значение (`selectedProxy` на момент взвода) используется лишь как признак: запускается текущий выбранный сервер.

### Влияние
Редкий, но неожиданный для пользователя запуск VPN после обновления: он держал VPN выключенным и не включал автозапуск,
а трафик внезапно пошёл через туннель (в том числе в режиме «Белые списки» или через сервер, которым пользователь
сейчас пользоваться не хотел). Вред небольшой, но это расхождение между тем, что пользователь выбрал, и тем, что делает
сервис.

### Как воспроизвести
Шаги выведены из кода, не прогонялись.
1. VPN включён. «Проверить обновления» → «Обновить». Пока идёт загрузка, свернуть приложение, чтобы подтверждение
   установки пришло уведомлением; уведомление не открывать. Открыть окно обновления и нажать «Закрыть» в состоянии
   «Установка».
2. Убедиться, что флаг взведён: значение `resumeAfterUpdate` в базе настроек (`adb shell run-as dev.folki.crown.debug`,
   таблица настроек) не равно 0.
3. Выключить VPN; «Подключаться при запуске» выключено.
4. Выполнить встроенное обновление ещё раз (или `adb install -r` той же сборки) и дождаться окончания установки.
5. Фактический результат: VPN включается сам после установки. Ожидаемый: остаётся выключенным.

## What Changes
- Рекомендуется: хранить вместе с флагом цель (`versionCode` предложения) и время взвода. `PackageReplacedReceiver`
  поднимает VPN, только если установленный `versionCode` равен ожидаемому и с момента взвода прошло немного времени
  (например, не больше часа); в остальных случаях флаг просто сбрасывается.
- В `download()` при выключенном сервисе явно сбрасывать флаг (`resumeAfterUpdate = 0`), а не оставлять старое значение.
- В `dismiss()` из состояния «Установка» флаг не сбрасывать: подтверждение установки может ждать в уведомлении, и после
  позднего подтверждения VPN должен подняться. От залежавшегося флага защищают проверки версии и срока из первого
  пункта; явный сброс — только при окончательном отказе или отмене (`fail()`, как сейчас).
- VPN, который пользователь выключил сам, после позднего подтверждения той же установки подниматься не должен:
  ручная остановка сбрасывает флаг (или приёмник не поднимает VPN, если после взвода была ручная остановка). В тест
  решения приёмника добавляется случай «взвод → ручная остановка → подтверждение установки».
- Проверка: сценарий выше — после шага 4 VPN не включается; обычное самообновление при включённом VPN по-прежнему
  поднимает VPN после установки.

## Impact
- **Код:** `update/UpdateManager.kt` (`download`, `dismiss`), `BootReceiver.kt` (`PackageReplacedReceiver`), `DataStore` /
  `Constants.kt` при хранении цели и времени.
- **Upstream:** все файлы — код upstream вне списков точек правки: нужна новая точка правки или патч в upstream.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** если пользователь подтвердит установку позже порога, VPN после неё не поднимется сам — приемлемо, он
  включит его вручную. Ключ `resumeAfterUpdate` числится в `ANDROID_KEYS` (`SettingsRegistry.kt:389`) и в
  `DEVICE_LOCAL_KEYS` — резервная копия его не переносит (`:401`); новые поля должны попасть в те же списки.
- **Проверка исправления:** сценарий 1–5 до и после; юнит-тест решения приёмника по (флаг, versionCode, время, автозапуск).
- **Внешние источники:**
  - `Intent.ACTION_MY_PACKAGE_REPLACED`: https://developer.android.com/reference/android/content/Intent#ACTION_MY_PACKAGE_REPLACED
  - `PackageInstaller.STATUS_PENDING_USER_ACTION`: https://developer.android.com/reference/android/content/pm/PackageInstaller#STATUS_PENDING_USER_ACTION
