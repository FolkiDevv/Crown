# Proposal

> **Категория:** надёжность · **Приоритет:** средний · **Проверка:** подтверждено по коду · **Код:** upstream · **Объём:** M

## Why

### Находка
Восстановление резервной копии заменяет таблицы целиком и сохраняет id строк из копии:
```kotlin
// app/src/main/java/io/nekohasekai/sagernet/database/backup/BackupRestore.kt:352-359
SagerDatabase.instance.runInTransaction {
    val db = SagerDatabase.instance.openHelper.writableDatabase
    db.execSQL("PRAGMA defer_foreign_keys = ON")
    if (choice.profiles) {
        db.execSQL("DELETE FROM `$PROFILES`")
        db.execSQL("DELETE FROM `$GROUPS`")
        insertRows(db, GROUPS, staged.groups!!)
        insertRows(db, PROFILES, staged.profiles!!)
```
После коммита id 17 может принадлежать совсем другому серверу или группе (копия с компьютера, со старого телефона, давняя
копия этого телефона). Транзакция атомарна, но перед ней `BackupFragment.restore` (UI-процесс) останавливает только VPN и
ждёт этого не дольше 5 с, после чего продолжает в любом случае (`ui/BackupFragment.kt:428-456`,
`withTimeoutOrNull(5000L) { while (running()) delay(100L) }`).

Очередь обновления подписок и тесты работают в процессе `:bg`, и общей блокировки с восстановлением нет:
`SubscriptionQueue.awaitIdle()` (`group/SubscriptionQueue.kt:294`) существует, но из восстановления не вызывается.
Обновление подписки держит снимок группы, прочитанный до сетевого запроса, и пишет частями в отдельных транзакциях:
- `group/SubscriptionRefresh.kt:384` — `members = ProfileManager.members(gid)` до загрузки;
- `:144` — `batchDeleteProfiles(stale)` по старым id удаляет восстановленные профили с теми же id;
- `:587-593` — `updateOutbound(entry.supersedes, …)` по старым id записывает сервер подписки поверх восстановленной строки;
- `:609-616` — `addProfileBatch(chunk, gid)`: после восстановления `gid` — чужая или несуществующая группа; ошибка внешнего
  ключа проглатывается (`catch (e: Exception) { Logs.w(e) }`).

Тесты так же пишут результаты по id профиля. Если VPN не остановился за 5 с, остановка позже прибавит трафик старого сеанса
к восстановленным профилям с теми же id. Перезапуск процессов (`triggerFullRestart`) происходит только после нажатия OK в
диалоге «Восстановлено» (`BackupFragment.kt:458-474`) — до этого фоновые записи успевают пройти.

### Влияние
Редкий, но реальный сценарий: перенос настроек на новый телефон или откат на копию, пока идёт автообновление подписки
(периодическое) или обновление, запущенное минуту назад на медленной панели. После восстановления часть профилей молча
содержит чужие серверы, часть восстановленных профилей пропадает, серверы подписки попадают в чужую группу. Ошибка не
показывается. На свежих установках id начинаются с 1 и в копии, и на устройстве — пересечение id вероятно.
`backup-restore`, требование «Restore validation»: восстановление должно дать данные копии.

### Как воспроизвести
Шаги выведены из кода и не прогонялись.
1. Сделать копию с группой «Мои серверы» из 2–3 серверов (на другом устройстве или до шага 2).
2. На тестовом устройстве завести подписку с большим числом серверов на медленном локальном сервере: HTTP-сервер на хосте,
   который отвечает через 20–30 с (`adb reverse tcp:8099 tcp:8099`, подписка `http://127.0.0.1:8099/sub`).
3. «Обновить» подписку и сразу «Резервная копия → Восстановить» с файлом из шага 1, все части.
4. Дождаться диалога «Восстановлено», 30 с не нажимать OK, затем нажать.
5. Ожидаемый неверный результат: в группе «Мои серверы» часть серверов заменена серверами подписки или исчезла, либо
   появились лишние; в logcat от обновления — удаления или `FOREIGN KEY constraint failed`.

## What Changes
- Рекомендуется: сделать восстановление монопольной операцией над БД. Перед коммитом завершить процесс `:bg` (очередь
  подписок, тесты, VPN) и не давать ему подняться до перезапуска приложения; если VPN не остановился за отведённое время —
  не восстанавливать, а сообщить об ошибке. Так как восстановление идёт в UI-процессе, а очередь — в `:bg`, завершение `:bg`
  проще и надёжнее паузы очереди через AIDL.
- Перезапускать процессы сразу после коммита, а предупреждения показывать после перезапуска (сохранив их), а не ждать OK.
- Вариант мягче: через AIDL поставить очередь подписок на паузу и дождаться простоя (`awaitIdle` с флагом «не брать новые
  задания»), отменить идущие тесты; показывать «Ждём завершения обновления подписок…» с кнопкой отмены.
- Дешёвая страховка: обновление подписки перед каждой записью проверяет, что группа `gid` осталась той же (например,
  совпадает URL), и прекращается, если нет.
- Проверка: сценарий выше даёт ровно содержимое копии.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `backup-restore`: в «Restore validation» добавляется — восстановление выполняется, только когда фоновые записи
  (обновление подписок, тесты, учёт трафика) остановлены, и ни одна из них не пишет в БД до перезапуска.

## Impact
- **Код:** `ui/BackupFragment.kt`, `database/backup/BackupRestore.kt`; для мягкого варианта — `group/SubscriptionQueue.kt`,
  AIDL сервиса, тестовые раннеры в `bg/test/`.
- **Upstream:** все файлы — код upstream вне точек правки; нужна новая точка правки или патч в upstream (на десктопе другой
  процессный механизм, но та же проблема с фоновыми записями).
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** ожидание простоя очереди на медленной панели может длиться минуту — нужен индикатор и отмена. Перенумеровывать
  id при восстановлении не стоит: это ломает совместимость с копиями десктопа (ссылки между таблицами по id).
- **Проверка исправления:** сценарий «Как воспроизвести»; инструментальный тест: восстановление при идущем обновлении
  подписки — содержимое таблиц совпадает с копией.
- **Внешние источники:** нет.
