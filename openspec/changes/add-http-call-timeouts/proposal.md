# Proposal

> **Категория:** стабильность, надёжность · **Приоритет:** средний · **Проверка:** воспроизведено на эмуляторе ·
> **Код:** upstream · **Объём:** S (общий срок запроса), M (ожидания с таймаутом в очереди)

## Why

### Находка
Все HTTP-клиенты приложения задают только таймауты неактивности и не задают общий срок вызова:

```kotlin
// app/src/main/java/io/nekohasekai/sagernet/ktx/Nets.kt:143-148 (httpGet — загрузка подписок)
val builder = OkHttpClient.Builder()
    .connectTimeout(10, TimeUnit.SECONDS)
    .readTimeout(10, TimeUnit.SECONDS)
    .writeTimeout(10, TimeUnit.SECONDS)
    .followRedirects(false)
    .followSslRedirects(false)
```

То же в `newHttpClient` (`Nets.kt:62-65`: `fetchText` для rule-set'ов, маршрутных профилей, конфигурации simple и
проверки обновлений) и в `appHttpClient` (`Nets.kt:259-262`: гео-базы, проверка IP выхода). `callTimeout` в коде нет
нигде. В OkHttp read timeout считается для каждого чтения из сокета отдельно, а `callTimeout` по умолчанию равен 0 —
без ограничения. Ответ, который приходит по нескольку байт раз в 9 с, никогда не упирается в таймаут. Тело подписки
читается до 64 МиБ (`SubscriptionFetch.kt:70-77`, `readCapped` в `Nets.kt:294-303`). `httpGet` к тому же сам проходит
до 20 перенаправлений (`Nets.kt:206-229`), и у каждого перехода свои таймауты.

Последствия сильнее всего в очереди подписок процесса `:bg`. Задачи выполняются строго по одной и без срока
(`group/SubscriptionQueue.kt:332-364`). Пока одна загрузка висит, стоят:
- обновления остальных подписок, ручные и автоматические (`SubscriptionScheduler.kt:172` ждёт `awaitIdle()`);
- импорт текста и ссылок: `importFile` ждёт свою задачу через `runBlocking { done.await() }` на потоке binder
  (`SubscriptionQueue.kt:251`). Из UI его вызывает `SubscriptionClient.importText` (`SubscriptionClient.kt:131-150`),
  то есть добавление сервера из буфера обмена или QR в simple (`simple/add/SimpleImport.kt:141`) и в классике;
- «Удалить невалидные» и «Разрешить домены»: `runQueued` → `runBlocking { result.await() }` (`SubscriptionQueue.kt:290`).

Отмена корутины или воркера WorkManager блокирующий `execute()` не прерывает: `call.cancel()` нигде не вызывается.
simple ждёт первое обновление новой подписки 120 с (`SimpleImport.kt:163`, `:190`) и показывает ошибку, но задача
в `:bg` продолжает держать очередь.

### Влияние
Сценарий реален для аудитории Crown: при DPI-замедлении соединение не рвётся, а «капает»; то же бывает на плохой
мобильной сети и с полуживым прокси, когда запросы идут через mixed inbound. Пользователь видит, что добавление сервера
из буфера или QR крутится без конца, другие подписки стоят «в очереди», действия с группой не отвечают. Без работающего
VPN ручные задачи держат `CoreService` в foreground типа dataSync, а на Android 15+ этот тип ограничен 6 часами в сутки:
зависшая задача тратит бюджет, и следующие тесты и обновления в тот день идут без foreground.

### Как воспроизвести
Проверено на эмуляторе Android 17, debug-сборка коммита `0a0fcc4e`, макет сервера подписки на хосте: тело 284 байта,
1 байт в секунду. Запрос начат в 00:45:49 (`[SubscriptionFetch] >>>>>>>> Requesting subscription`), закончен в 00:50:36
(`<<<<<<<< Subscription request finished`) — **4 мин 47 с** с индикатором на экране «Серверы», кнопки отмены нет.
Для сравнения: сервер, который не отвечает вовсе, даёт ошибку через 10 с — read timeout работает. Время растёт линейно
с размером тела: 64 КБ при 1 байт/с — около 18 часов. Шаги 3–4 (вторая подписка и импорт из буфера ждут) выведены из
кода очереди и на эмуляторе отдельно не прогонялись.

1. На хосте поднять HTTP-сервер, который на `GET /sub` отдаёт `200 OK` с заголовками и затем по 1 байту каждые 8 с
   (короткий скрипт: записать байт, сбросить буфер, подождать). Пробросить порт: `adb reverse tcp:8099 tcp:8099`.
2. Добавить подписку `http://127.0.0.1:8099/sub` и вторую — с обычным рабочим адресом.
3. Нажать «Обновить» у первой, затем у второй; затем в simple «Добавить» → вставить из буфера любую валидную ссылку `vless://`.
4. Наблюдать: вторая подписка остаётся «в очереди», импорт из буфера не завершается, пока работает сервер (минуты и часы);
   в logcat запрос первой подписки без завершения; `adb shell dumpsys activity services dev.folki.crown.debug` —
   `CoreService` в foreground.
5. Ожидаемый верный результат: первая подписка завершается ошибкой таймаута в пределах выбранного срока, вторая и импорт
   выполняются сразу после неё.

## What Changes
- Рекомендуется: в `Nets.kt` задать `callTimeout` во всех трёх фабриках клиентов. Для `httpGet` — общий срок на весь цикл
  перенаправлений: перед каждым переходом передавать оставшееся время (например, 120 с на запрос подписки). Для
  `fetchText` — 60 с. Для `appHttpClient`, где тело большое (гео-базы), — заметно больший срок или правило минимальной
  скорости. Ошибка таймаута уходит в штатный путь: старые серверы подписки остаются.
- Связать отмену задачи с отменой вызова: держать ссылку на `Call` и вызывать `cancel()` при отмене корутины (или
  `enqueue` + `suspendCancellableCoroutine`), чтобы остановка воркера действительно освобождала очередь.
- Дать в simple отмену идущего обновления подписки (очередь знает выполняемую группу, `runningGid`); сейчас кнопка
  «Обновить» на время загрузки заменяется индикатором.
- Дополнительно: ожидания на потоке binder (`importFile`, `runQueued`) ограничить по времени с понятной ошибкой («очередь
  занята, повторите позже») или сделать асинхронными с ответом через существующий callback.
- Проверка: сценарий выше до и после; юнит-тест на `httpGet` с MockWebServer, который отдаёт тело с задержкой
  (`throttleBody`) — запрос завершается ошибкой не позже срока.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `profile-management`: требование «Subscription update» дополняется — загрузка подписки ограничена общим сроком; медленный
  ответ одного источника завершается ошибкой и не задерживает другие подписки и импорт.

## Impact
- **Код:** `app/src/main/java/io/nekohasekai/sagernet/ktx/Nets.kt`; для отмены и ожиданий —
  `group/SubscriptionQueue.kt`, `group/SubscriptionFetch.kt`.
- **Upstream:** `Nets.kt` — существующая точка идентичности форка (`FORK_IDENTITY_POINTS`, User-Agent), но с новым
  назначением: описание нужно расширить. `SubscriptionQueue.kt` в списки не входит: изменения очереди требуют новой
  точки правки или патча в upstream (там тот же недостаток). Минимальная мера — только `callTimeout` в `Nets.kt`.
- **Ядро throne, сборка, инструменты:** ядро не затрагивается; `tools/diagnostics/upstream_touch_points.py` — описание точки.
- **Риски:** слишком короткий срок оборвёт законно большую подписку на медленной сети — срок брать с запасом и показывать
  понятную ошибку. Системное разрешение имени отменой не прерывается: поток освободится, когда ответит резолвер.
- **Проверка исправления:** шаги 1–5; юнит-тест с MockWebServer.
- **Внешние источники:**
  - OkHttp 5.x, `OkHttpClient.Builder.callTimeout` (по умолчанию 0 — без ограничения): https://square.github.io/okhttp/5.x/okhttp/okhttp3/-ok-http-client/-builder/call-timeout.html
  - OkHttp 5.x, `OkHttpClient` (таймауты и отмена вызова): https://square.github.io/okhttp/5.x/okhttp/okhttp3/-ok-http-client/index.html
  - Foreground service timeouts (dataSync, Android 15): https://developer.android.com/develop/background-work/services/fgs/timeout
