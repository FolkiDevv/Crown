# Proposal

> **Категория:** скорость · **Приоритет:** низкий · **Проверка:** подтверждено по коду; число проходов частично
> подтверждено замерами на эмуляторе · **Код:** Crown · **Объём:** S–M

## Why

### Находка
Простой интерфейс много раз подряд пересчитывает одни и те же данные целиком: каталог серверов, «факты» подписок и
управляемые селекторы режимов.

**Каталог «Серверов».** `ServersViewModel.reload()` каждый раз выполняет полный `ServerCatalog.load`
(`app/src/simple/java/io/nekohasekai/sagernet/simple/servers/ServerCatalog.kt:25-44`). Он читает полные строки всех
групп (`proxyDao.getByGroup`, с `outbound_json`), разбирает JSON каждого профиля (`profile.outbound`: кэш живёт в
экземпляре `ProxyEntity`, а экземпляры новые на каждый запрос, `ProxyEntity.kt:70-92`) и определяет страну по имени
(`CountryFromName.detect`: если в имени нет флага, перебираются обе таблицы названий стран, `CountryFromName.kt:140-160`).
`reload()` вызывают:
- `init` и `SimpleActivity.onStart` (`ServersViewModel.kt:207`, `SimpleActivity.kt:385`) на каждом входе в приложение,
  даже если раздел не открыт;
- каждый этап фонового раунда тестов (`ServersViewModel.kt:557, 581, 607, 619, 635, 651, 685`);
- `onAdd`/`onRemoved` слушателя `ProfileManager` **на каждый профиль**, добавленный или удалённый в процессе UI
  (`ServersViewModel.kt:501-504`). При импорте или пакетном удалении получается серия чтений.

`reload()` отменяет предыдущее чтение (`:221`), но блокирующий `load()` внутри `withContext(Dispatchers.IO)` отмену
не проверяет. Начатое чтение доходит до конца, и его результат выбрасывается.

**Факты подписок.** `NoticesViewModel.reload()` (`subs/NoticesViewModel.kt:72-105`) вызывает `SubscriptionState.facts()`
(`subs/SubscriptionState.kt:55-62`). Это ещё один полный проход по серверам всех подписок с разбором JSON, только чтобы
найти «заглушки». Он идёт из `init`, после каждого обновления и из `resumed()` на каждом `onStart`
(`SimpleActivity.kt:387`). При этом `ServersViewModel.load()` уже считает те же факты по своему каталогу
(`ServersViewModel.kt:468-474`).

**Режимы.** При создании `ModesViewModel` в `init` выполняется `TrafficModeApplier.ensure` (`modes/ModesViewModel.kt:84-101`),
и сразу же `onStart` вызывает `syncGroups()` — второй такой же `ensure` (`ModesViewModel.kt:238-249`, `SimpleActivity.kt:382-384`).

### Влияние
Главный поток не блокируется, всё идёт на фоновом пуле. Эффект — лишний ЦП и мусор для GC на больших подписках.
Замеры release-сборки на эмуляторе Android 17 (4 vCPU, эмулятор был загружен, абсолютные числа завышены):
- холодный старт с 3000 серверами — 6 полных выборок группы в фоне, 37 мс SQL. Время старта от числа серверов почти не
  зависит: медиана 2282 мс без серверов и 2835 мс с 3000 при разбросе p90 3782/3927 мс;
- добавление подписки — 35 полных выборок (500 серверов) и 30 (3000 серверов, 1,56 с SQL) в процессе UI, параллельно
  со сводкой «Подписка добавлена»;
- фоновый раунд тестов 3000 серверов — за 4 мин ЦП процесса UI ≈3,2 с пользовательского времени. Перечитывания каталога
  составляют его часть.

Разбор JSON и определение страны в эти числа SQL не входят и отдельно не измерялись. Заметнее всего эффект на слабых
устройствах и Android TV при добавлении подписки и пакетных удалениях. Обычный вход в приложение он почти не замедляет.

### Как воспроизвести
Шаги выведены из кода. Счётчики выборок взяты из системной трассы `atrace` (категория `database`), отдельный прогон
с логированием не делался.
1. Release- или debug-сборка, подписка на 3000 серверов (часть имён без флага), простой интерфейс.
2. Записать `atrace` с категорией `database` и снять: холодный старт с иконки; «Домой» → вернуться; добавление ещё одной
   подписки на 500 серверов.
3. Посчитать `SELECT * FROM profiles WHERE gid = ?` в процессе UI. Ожидается: ≥ 4 полных прохода на холодный старт (по 2 от
   `ServersViewModel` и `NoticesViewModel`), 2 на каждый возврат, 30–35 при добавлении подписки.
4. Для точной цены временно обернуть `ServerCatalog.load` и `SubscriptionState.facts` в `Trace.beginSection` и посмотреть
   их длительность в Perfetto.

## What Changes
1. **Слить серии.** `reload()` при уже идущем чтении не начинает новое, а ставит флаг «перечитать ещё раз после текущего».
   Для `onAdd`/`onRemoved` достаточно одного чтения после серии (короткая задержка около 200 мс). В `ServerCatalog.load`
   между группами вызывать `ensureActive()`, чтобы отменённое чтение прекращалось. Это рекомендуемый первый шаг:
   он убирает 30–35 чтений при импорте и не меняет поведение.
2. **Один проход вместо двух на `onStart`.** `NoticesViewModel` берёт факты подписок из последнего каталога
   `ServersViewModel` (тот уже считает `factsOf(group, usable, placeholders)`) или из общего кэша процесса с ключом
   `subLastUpdate` + число серверов группы. Тогда `facts()` не читает серверы, если подписка не обновлялась.
3. **Не повторять `ensure` подряд.** `syncGroups()` из первого `onStart` пропускается, если `init` только что выполнил
   `ensure` (или `apply`) в этом же процессе.
4. Необязательно: кэшировать результат `CountryFromName.resolve` по строке имени на время жизни процесса.

Как проверить: в сценарии выше ≤ 2 полных прохода на холодный старт, ≤ 1 на возврат, ≤ 2–3 при добавлении подписки.
Список серверов, карточки подписок и сообщения на главной показывают то же, что до изменения (тесты `SubscriptionNotices`).

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
(нет) — меняется только частота чтений. Требования `simple-ui` («Структура списка серверов», «Сообщения подписки») и
`traffic-modes` не меняются.

## Impact
- **Код:** `simple/servers/ServersViewModel.kt`, `simple/servers/ServerCatalog.kt`, `simple/subs/NoticesViewModel.kt`,
  `simple/subs/SubscriptionState.kt`, `simple/modes/ModesViewModel.kt`, `simple/SimpleActivity.kt`.
- **Upstream:** только код Crown.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** при слиянии серий нельзя потерять последнее изменение (флаг «перечитать после текущего», а не простой
  пропуск). Кэш фактов подписки должен сбрасываться и при ручном изменении серверов группы в classic, а не только по
  `subLastUpdate`. Порядок `ensure` до чтения сервера на главной (сервер «Авто» на карточке) нужно сохранить.
- **Проверка исправления:** счётчики выборок в `atrace` до и после; существующие JVM-тесты simple UI.
- **Связанные изменения:** автоматический раунд тестов при каждом открытии «Серверов» (отдельный proposal об ограничении
  автоматических тестов) — отдельная и более крупная причина нагрузки. После него число перечитываний за раунд
  уменьшится само.
