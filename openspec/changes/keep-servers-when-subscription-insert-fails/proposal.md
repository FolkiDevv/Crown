# Proposal

> **Категория:** надёжность · **Приоритет:** средний · **Проверка:** подтверждено по коду ·
> **Код:** upstream · **Объём:** S (не глотать ошибку), M (одна транзакция на группу)

## Why

### Находка
Обновление подписки пишет в базу несколькими отдельными транзакциями: вставка новых серверов кусками, обновление
изменившихся на месте, удаление устаревших. Ошибка вставки ловится и только пишется в журнал:

```kotlin
// app/src/main/java/io/nekohasekai/sagernet/group/SubscriptionRefresh.kt:606-616 (ImportSink.flush)
suspend fun flush() {
    if (chunk.isEmpty()) return
    try {
        val rows = ProfileManager.addProfileBatch(chunk, gid)
        rows.forEachIndexed { i, row -> entries[entryIndex[i]].id = row.id }
    } catch (e: Exception) {
        Logs.w(e)
    }
    chunk.clear()
    entryIndex.clear()
}
```

Невставленные записи остаются с `id = -1` («not stored», `SubscriptionReconcile.kt:107-108`). Дальше:
1. `SubscriptionReconcile.reconcile` относит к устаревшим все старые серверы, которые не совпали с новыми ни по
   содержимому, ни по identity или имени (`SubscriptionReconcile.kt:78-82`); записи с `id < 0` просто выпадают из
   порядка (`:89`).
2. `update()` удаляет устаревшие (`SubscriptionRefresh.kt:144`); флаг `dbFailed` выставляется только при ошибке удаления
   (`:145-148`).
3. Время обновления пишется без проверки каких-либо ошибок записи (`SubscriptionRefresh.kt:208-211`), отчёт показывает
   «[-] удалено N» без соответствующих «[+]».

Защита «пустой ответ не стирает группу» здесь не срабатывает: разбор прошёл успешно, отказала запись. Обновление на
месте (`:584-599`) ошибку не глотает — его исключение доходит до очереди и показывается пользователю; проблема только
во вставке.

Дополнительно: `ProfileManager.addProfileBatch` (`database/ProfileManager.kt:146-161`) пишет куски в отдельных
транзакциях. Если упадёт второй кусок, первый уже в базе, но исключение теряет весь список `rows` — записанные строки
остаются в группе без места в её порядке. Похожий риск у настройки «Очищать серверы перед обновлением» (`sub_clear`,
по умолчанию выключена, `SettingsRegistry.kt:293`): все члены группы удаляются до вставки новых (`SubscriptionRefresh.kt:395-412`).

### Влияние
Подписка теряет серверы, которые провайдер сменил (новые адреса, ключи, протокол), хотя в ответе они есть. Если удалён
выбранный сервер, выбор сбрасывается; если удалён работающий — VPN переключается на преемника или останавливается.
Время обновления записано, поэтому автообновление повторит попытку только через интервал (в simple — сутки). Ошибку
пользователь не видит, видит только, что серверов стало меньше. Восстанавливается ручным обновлением, если запись к тому
времени снова работает.

Когда вставка отказывает: заполнен раздел данных (`SQLiteFullException`), база повреждена, второй процесс держит
блокировку записи дольше допустимого ожидания (длинная транзакция в UI: импорт, сортировка, восстановление копии).
Сценарий редкий, но потеря тихая.

### Как воспроизвести
Шаги выведены из кода, не прогонялись.
1. Тест (JVM с Robolectric или инструментальный): группа-подписка с 10 серверами; ответ подписки — те же 10, но у 5
   сменились адрес, ключ и имя (не совпадают ни по содержимому, ни по identity, ни по имени).
2. Подменить вставку (`ProfileManager.addProfileBatch` или DAO `insert`), чтобы она бросала `SQLiteFullException`.
3. Выполнить обновление группы.
4. Фактический результат: в группе 5 серверов, время обновления подписки новое, ошибки в очереди подписок нет.
   Ожидаемый: 10 исходных серверов, время не изменилось, показана ошибка базы данных.
5. На эмуляторе: заполнить раздел данных (`adb shell dd if=/dev/zero of=/data/local/tmp/fill bs=1m` до ENOSPC) и вручную
   обновить подписку, у которой сменились серверы; в logcat — `SQLiteFullException` из `flush`, затем строки `[-]`
   в журнале обновления.

## What Changes
- Рекомендуется (минимально): `ImportSink.flush` запоминает отказ вставки. Если он был, `update()` не удаляет устаревшие
  серверы, не пишет время обновления и сообщает ошибку базы данных (`dbError(gid)`), как уже делается для удаления.
  Новые строки, которые успели записаться, следующее обновление найдёт по содержимому.
- При включённом `sub_clear` этого мало: `loadSnapshot` удаляет серверы **до** вставки
  (`SubscriptionRefresh.kt:395-398`), и отказ вставки их уже не вернёт. Для `sub_clear` и в минимальном варианте
  удаление переносится после успешной вставки (или удаление и вставка идут одной транзакцией).
- После отказа вставки обновление завершается сразу, до фильтров: `SubscriptionFilters.removeFlagged`
  (`SubscriptionRefresh.kt:195`) и любые другие удаления не выполняются, иначе сохранённый старый сервер уйдёт через них.
- Время обновления не писать и при `dbFailed` по другим причинам (ошибка удаления, фильтров): тогда автообновление
  повторит попытку раньше.
- Лучше (M): выполнить вставку, обновление на месте, удаление и запись порядка одной транзакцией Room на группу. Отказ
  записи или смерть процесса посередине тогда оставляют группу в прежнем состоянии. Для `sub_clear` — удалять в той же
  транзакции после вставки.
- Проверка: тест из шагов 1–4 после исправления оставляет 10 исходных серверов, время обновления прежнее, показана ошибка.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `profile-management`: требование «Subscription update» дополняется сценарием «Сбой записи в базу»: если новые серверы
  не удалось сохранить, существующие серверы группы не удаляются, время обновления не меняется и показывается ошибка.

## Impact
- **Код:** `group/SubscriptionRefresh.kt` (`ImportSink`, `update`, очистка перед обновлением); для варианта с одной
  транзакцией — `database/ProfileManager.kt`.
- **Upstream:** `SubscriptionRefresh.kt` — существующая точка правки 9, но только для вызовов хуков simple: исправление
  логики — новое назначение. Рекомендуется патч в upstream (там тот же недостаток) или расширение описания точки 9.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** одна большая транзакция на тысячи строк дольше держит блокировку записи, и запись UI-процесса будет ждать;
  при недопустимой задержке хватит минимального варианта. Неудача из-за заполненного диска будет повторяться при каждом
  автообновлении — сообщение должно говорить о причине.
- **Проверка исправления:** тест из «Как воспроизвести»; существующие тесты сверки подписки.
- **Внешние источники:**
  - Room `RoomDatabase.runInTransaction`: https://developer.android.com/reference/androidx/room/RoomDatabase#runInTransaction(java.lang.Runnable)
