# Proposal

> **Категория:** скорость, надёжность · **Приоритет:** средний · **Проверка:** воспроизведено на эмуляторе ·
> **Код:** upstream · **Объём:** S–M

## Why

### Находка
Перед стартом профиля автовыбора (режим «Авто» простого интерфейса) `:bg` ранжирует участников URL-тестом и ждёт результата:

- `bg/proto/ProxyInstance.kt:52-55` — `init()` вызывает `AutoSelectorRuntime.beforeStart(this)` до сборки конфигурации;
- `bg/autoselector/AutoSelectorRuntime.kt:137-140` — если `needsRanking(selectorId)`, то `measure(...)`, который ждёт
  `ready.await()` (`:414-415`) до кворума работающих участников или до конца всех тестов;
- `bg/autoselector/AutoSelectorProfiles.kt:155-170` — список `sweep.needed` вычисляется **до** ожидания, затем
  `TestEngine.queueUrlTests(sweep.needed, sweep::onResult)`;
- `bg/test/TestEngine.kt:105-107`:
  ```kotlin
  suspend fun queueUrlTests(ids: List<Long>, onResult: ((ProxyEntity) -> Unit)? = null) {
      if (ids.isEmpty()) return
      session.lock()
  ```
  Это та же блокировка, которую любая тестовая сессия держит всё время прогона (`TestEngine.kt:24`, `:33`).

Срока ожидания нет нигде по цепочке. Если блокировку держит другая сессия — URL-тест раздела «Серверы» (запускается сам при
каждом открытии раздела, см. `limit-automatic-server-tests`), ручной тест группы, тест скорости, URL-тест после обновления
подписки (`group/SubscriptionQueue.kt:302-307`), — VPN стоит в «Подключение», пока та не закончится. После этого `:bg`
тестирует `sweep.needed`, вычисленный до ожидания, то есть **повторно проверяет серверы, которые чужая сессия только что
проверила**.

Ранжирование перед стартом нужно, только если подходящих участников больше лимита сборки (`buildLimit = 300`) и в сборку
попал участник без свежего результата (`outbound/config/AutoSelectorPlan.kt:273-275`, срок годности результата —
`resultValidityMins = 1440`): большие подписки, несколько подписок в «Авто», первый старт после добавления подписки или
после суток без тестов.

Второй, гипотетический путь к бесконечному ожиданию: сам тест ждёт `onDone` от ядра без страховочного срока
(`bg/test/TestProbe.kt:100-105`); если ядро не вызовет его, блокировка не освободится до перезапуска `:bg`. Подтвердить можно
только со стороны ядра.

### Влияние
Пользователь добавил большую подписку (раздел «Серверы» при этом сам запускает тест всех серверов) и сразу нажимает
«Подключить» — VPN минутами в «Подключение», в уведомлении «Auto: measuring 472 profiles…», хотя первые минуты ничего не
измеряется. Нажатие «Отменить подключение» отменяет ранжирование — VPN не поднимается вовсе. Весь этот срок трафик идёт
напрямую.

Замер на эмуляторе (ниже): **5 мин 8 с** от «Connect» до старта ядра, из них ≈2 мин 35 с — ожидание чужой сессии и
≈2 мин 33 с — повторный тест тех же 472 серверов. Рабочие серверы нашлись в первые секунды обоих прогонов («2 OK»), но
досрочного старта по кворуму не было.

### Как воспроизвести
Эмулятор Android 17, debug-сборка `0a0fcc4e`, простой интерфейс, режим «Авто», журнал уровня info.
1. Подписка из 2 рабочих локальных серверов и вторая из 502 серверов (2 рабочих + 500 адресов TEST-NET `192.0.2.0/24`,
   которые не отвечают) — всего 504.
2. Добавить вторую подписку через «Серверы» → «Add server»: раздел «Серверы» сам запускает
   «URL test · 504 selected profiles».
3. Сразу нажать «Connect» (01:56:39 UTC).
4. Фактически (уведомления и `files/core.log`):
   ```
   04:56:40 [Auto selector] Measuring 472 not-yet-tested profiles...
   01:56:55 … 01:58:59  «URL test · 504 selected profiles»  82 → 460 / 504 · 2 OK   |  «Auto: measuring 472 profiles…»
   01:59:14 … 02:01:40  «URL test · 10.0.2.2»  0 → 450 / 472 · 2 OK            (повторный тест тех же серверов)
   05:01:47 [Auto selector] Ranked 4 profiles.
   05:01:47 Start: {…}
   05:01:48 [Auto selector] Running the best 4 of 4 ranked profiles.
   ```
   (Время в журнале приложения сдвинуто на +3 ч относительно UTC уведомлений.) Всё это время главная показывает
   «Cancel connecting».

## What Changes
1. (рекомендуется) Дать ранжированию перед стартом срок на захват блокировки: если `TestEngine` занят чужой сессией дольше
   нескольких секунд (3–5 с), стартовать на пуле как есть — как это уже делается, когда другой прогон ранжирования идёт
   (`AutoSelectorRuntime.kt:372-379`), — и доранжировать в фоне после освобождения движка; при изменении лучших пересобрать
   (механизм уже есть, `finishEarly`, `:430-444`). Ядро автовыбора само пробует участников, поэтому старт без ранжирования
   безопасен.
2. После получения блокировки пересчитывать `sweep.needed`: участники, получившие свежий результат за время ожидания, не
   тестируются повторно (результаты чужой сессии уже в БД).
3. Альтернатива для фоновых сессий: при старте VPN останавливать неинтерактивные тесты (раздел «Серверы», тест после
   обновления подписки) и отдавать блокировку ранжированию; ручной тест пользователя не трогать, но показывать «Ждём
   окончания теста», а не «measuring».
4. Страховка: срок ожидания `onDone` в `TestProbe` (таймаут × число пачек + запас), после которого `Mobile.stopTests()` и
   оставшиеся участники считаются не измеренными.

Проверка: тот же сценарий — время от «Connect» до `Start:` не больше выбранного срока + время старта ядра; в журнале нет
второго прогона по только что проверенным серверам.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `auto-selector`: «Automatic node selection» — старт соединения не ждёт без срока чужую тестовую сессию; ранжирование,
  которому мешает занятый движок, продолжается после старта.
- `proxy-connection`: «Connection state machine» — состояние Connecting не держится неограниченно из-за ожидания тестового движка.

## Impact
- **Код:** `bg/autoselector/AutoSelectorRuntime.kt` (`beforeStart`, `measure`), `bg/autoselector/AutoSelectorProfiles.kt`
  (`rank`), `bg/test/TestEngine.kt` (захват блокировки с ожиданием по сроку), при п. 4 — `bg/test/TestProbe.kt`.
- **Upstream:** **патч в upstream** — этих файлов нет в `TOUCH_POINTS`. Частичная мера на стороне Crown (меньше
  автоматических тестов из простого интерфейса) — в `limit-automatic-server-tests`, но она не закрывает ручные тесты и тест
  после обновления подписки.
- **Ядро throne, сборка, инструменты:** ядро не меняется (кроме гипотезы п. 4 о неприходящем `onDone`).
- **Риски:** старт без ранжирования может первые секунды работать на неотвечающих участниках, пока ядро их не отбракует;
  поведение расходится с desktop («waiting for any running test session», `AutoSelectorProfiles.kt:131-132`).
- **Проверка исправления:** сценарий выше; JVM-тест: `queueUrlTests` с занятым движком возвращает управление по сроку, а
  пересчёт `needed` исключает участников со свежими результатами.
