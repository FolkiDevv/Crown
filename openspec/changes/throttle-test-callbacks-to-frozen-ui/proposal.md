# Proposal

> **Категория:** стабильность, скорость · **Приоритет:** средний · **Проверка:** подтверждено по коду ·
> **Код:** upstream · **Объём:** S–M

## Why

### Находка
Процесс `:bg` шлёт в UI-процесс поток `oneway`-вызовов, не зная, виден ли UI и не заморожен ли его процесс.

1. **Тест скорости.** Ядро опрашивается каждые 100 мс, и каждый образец уходит клиенту отдельной транзакцией:
   `app/src/main/java/io/nekohasekai/sagernet/bg/test/SpeedTestRunner.kt:173` `delay(SPEED_POLL_INTERVAL_MS)`
   (`:264` `= 100L`) → `:182` `session.speedProgress(...)` →
   ```kotlin
   // bg/test/TestSession.kt:353-356
   fun speedProgress(snapshot: SpeedTestSnapshot) {
       notification.speed(snapshot)
       notifyClient { it.onSpeedProgress(snapshot) }
   }
   ```
   `ITestSessionCallback` объявлен `oneway interface` (`app/src/main/aidl/io/nekohasekai/sagernet/aidl/ITestSessionCallback.aidl:9`),
   `SpeedTestSnapshot` — Parcelable из 16 полей со строками.
2. **URL-, IP- и сервисные тесты.** Результаты приходят пачками, но в UI уходят по одной транзакции на сервер
   (`TestSession.kt:260-312`: `onUrlResult`, `onIpResult`, `onServiceResult`).
3. `notifyClient` (`TestSession.kt:388-399`) прекращает отправку только после `RemoteException`; видимость клиента не
   учитывается.

Все сервисы и ресиверы приложения работают в `:bg` (`AndroidManifest.xml`, `android:process=":bg"`), поэтому UI-процесс
без видимой activity становится cached, и на современных Android система его замораживает — на эмуляторе Android 17 это
видно в logcat: `ActivityManager: freezing <pid> dev.folki.crown.debug`. По документации AOSP oneway-транзакции к
замороженному процессу копятся в его буфере, а при переполнении буфера система убивает процесс-получатель с причиной
`ApplicationExitInfo.REASON_FREEZER`.

Для статуса автовыбора защита уже есть: публикация пропускается при выключенном экране, неизменённый статус не
отправляется, канал отправки «последнее значение» (`bg/autoselector/AutoSelectorRuntime.kt:553-555`, `:588-597`, `:99-104`).
Остаётся случай «экран включён, пользователь в другом приложении» — транзакции только при реальном изменении статуса.

### Влияние
Пользователь запускает тест скорости нескольких серверов или URL-тест большой подписки и переключается в другое приложение
(тест идёт минутами — обычное поведение). Оценка без замера: одна транзакция `onSpeedProgress` — около 0,5 КБ, 10 в секунду —
около 5 КБ/с; буфер асинхронных транзакций (порядка половины от ~1 МБ) заполняется примерно за 1,5–2 минуты теста скорости
в фоне. `onUrlResult` — около 0,3 КБ: переполнение после ~1500 результатов, то есть URL-тест одной большой подписки.
Последствия: система убивает UI-процесс; VPN и тест в `:bg` продолжают работать, но при возврате приложение стартует
холодно, панель теста пропадает (состояние клиента теста было только в памяти), а новый тест до конца старой сессии получает
отказ «занято». Пока процесс заморожен, `:bg` тратит CPU на сериализацию тысяч транзакций, которые никто не прочтёт; после
разморозки UI разбирает пачку устаревших событий.

### Как воспроизвести
Шаги выведены из кода и не прогонялись; заморозка UI-процесса в фоне на эмуляторе Android 17 наблюдалась отдельно.
1. Эмулятор Android 16/17, debug-сборка. Проверить, что freezer включён: `adb shell dumpsys activity settings | grep -i freezer`.
2. Подписка с 20+ серверами. Запустить тест скорости группы, сразу нажать Home.
3. Через 10–20 с убедиться в заморозке: `adb logcat -d | grep "freezing .*dev.folki.crown.debug$"`.
4. Ждать 3–5 минут, затем `adb shell dumpsys activity exit-info dev.folki.crown.debug` — ожидаемый неверный результат:
   запись основного процесса с причиной FREEZER (14); в logcat — сообщения binder о переполнении async-буфера замороженного
   процесса.
5. Вариант для URL-теста: группа из 2000+ серверов, «Тест URL» группы, Home, тот же контроль.

## What Changes
- Рекомендуется: не слать поток событий невидимому или замороженному клиенту.
  - `onSpeedProgress` — не чаще 1–2 раз в секунду и только последнее значение (уведомление теста и так обновляется своим
    циклом раз в секунду).
  - Результаты URL/IP/сервисных тестов — одним вызовом со списком на пачку вместо вызова на сервер.
  - UI сообщает `:bg` свою видимость (как это уже сделано для трафика: `TrafficLooper` шлёт скорость только колбэку переднего
    плана). Пока UI не виден, `:bg` шлёт только `onDone`; при возврате UI перечитывает итог из БД (результаты и так
    сохраняются в `:bg`) и счётчики сессии отдельным вызовом.
- На Android 16+ дополнительно `IBinder.addFrozenStateChangeCallback` на binder клиента: пока он заморожен, ничего не слать.
- Для `cbAutoSelectorUpdate` — та же проверка видимости вместо одного признака «экран включён».
- `onDone` и итоговые результаты отправляются всегда.
- Проверка: сценарий выше — до исправления UI убит с REASON_FREEZER, после — нет; число транзакций `ITestSessionCallback`
  за тест скорости 20 серверов падает с ~10/с до ≤ 1/с (`dumpsys binder_calls_stats` или счётчик в debug-сборке).

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `connectivity-testing`: в «Batch testing» добавляется — пока интерфейс не виден, сервис не шлёт поток промежуточных
  событий; итог теста доступен интерфейсу при возврате.
- `proxy-connection`: в «UI process binding» уточняется — сервис учитывает видимость и заморозку клиента при рассылке
  колбэков.

## Impact
- **Код:** `bg/test/TestSession.kt`, `bg/test/SpeedTestRunner.kt`, `aidl/.../ITestSessionCallback.aidl` (пакетный вызов),
  `ui/test/TestSessionClient.kt`; для автовыбора — `bg/autoselector/AutoSelectorRuntime.kt`.
- **Upstream:** код upstream, точек правки форка здесь нет — нужны новые точки правки или патч в upstream (там та же проблема).
  Simple использует тот же `TestSessionClient`, значит исправление закрывает оба интерфейса.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** изменение AIDL требует одновременной правки обеих сторон (они в одном APK — проблем совместимости нет). Потеря
  промежуточных событий допустима, потеря `onDone` — нет. Список в UI будет обновляться пачками; UI и сейчас публикует
  состояние не чаще раза в 100 мс.
- **Проверка исправления:** сценарий «Как воспроизвести» до и после; счётчик транзакций.
- **Внешние источники:**
  - AOSP, «Handle cached and frozen apps» (буферизация oneway, убийство при переполнении, `addFrozenStateChangeCallback`): https://source.android.com/docs/core/architecture/ipc/binder-freezer
  - AOSP, «Cached apps freezer»: https://source.android.com/docs/core/perf/cached-apps-freezer
