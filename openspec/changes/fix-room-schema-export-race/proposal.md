# Proposal

> **Категория:** надёжность · **Приоритет:** низкий · **Проверка:** подтверждено по коду (схемы 18–20); гонка экспорта —
> гипотеза · **Код:** upstream · **Объём:** S

## Why

### Находка
Схема базы Room экспортируется аргументом KSP, общим для всех вариантов сборки:

```kotlin
// app/build.gradle.kts:23-26
ksp {
    arg("room.incremental", "true")
    arg("room.schemaLocation", "$projectDir/schemas")
}
```

Две проблемы.

1. **Схемы текущих версий не в репозитории.** `@Database(version = 20)`
   (`app/src/main/java/io/nekohasekai/sagernet/database/SagerDatabase.kt:25`), а `git ls-files app/schemas` показывает
   только `8.json`, `9.json`, `11.json`–`17.json`. Файлы `18.json`–`20.json` не игнорируются — их просто не закоммитили.
   Пока это ничему не мешает: миграции 17→18, 18→19, 19→20 ручные (`SagerDatabase.kt:203`), а ручным миграциям схема не
   нужна. Но следующая `AutoMigration(from = 20, to = 21)` на чистом checkout (CI) не соберётся: Room требует схему
   исходной версии. Проверить миграции 17→20 тестом (`MigrationTestHelper`) тоже нечем, а при ошибке миграции
   `fallbackToDestructiveMigration()` (`SagerDatabase.kt:211`) молча пересоздаёт базу без профилей и подписок.
2. **Варианты пишут один и тот же файл.** `ksp<Variant>Kotlin` всех вариантов (`ossDebug`, `ossRelease`, `fdroid*`) пишут
   `app/schemas/<класс>/20.json`; Room 2.6 перед записью читает существующий файл, чтобы сравнить. При
   `org.gradle.parallel=true` (`gradle.properties:23`) задачи компиляции одного модуля могут выполняться одновременно,
   и одна может прочитать файл, который другая пишет. Это гипотеза: на запуске не наблюдалось. В CI гонки нет — там
   собирается один вариант за запуск (`.github/workflows/ci.yml:26`, `release.yml:56`); она возможна в локальных
   сборках нескольких вариантов одной командой. Кроме того, каталог, переданный строкой, не участвует в проверках
   up-to-date Gradle.

### Влияние
- Пользователя напрямую не задевает. Задевает разработку: первая авто-миграция после версии 20 потребует восстановить
  `20.json` из старого коммита; без тестов миграций ошибка в будущей миграции дойдёт до пользователей и сотрёт данные
  через `fallbackToDestructiveMigration()`.
- Если гонка случается — ложное падение локальной сборки или испорченный JSON схемы в рабочем дереве, который можно
  случайно закоммитить.

### Как воспроизвести
Шаги выведены из кода, не прогонялись.
1. `git ls-files app/schemas` — нет `18.json`…`20.json`; после любой сборки они появляются как неотслеживаемые файлы.
2. В ветке поднять версию до 21 с `AutoMigration(from = 20, to = 21)` и собрать на чистом checkout — ошибка Room о
   ненайденной схеме версии 20.
3. Для гонки: на чистом `app/build` 5–10 раз выполнить `./gradlew app:assembleOssDebug app:assembleOssRelease`
   и искать в выводе `MalformedJsonException` в задачах `kspOss*Kotlin`. Если ни разу — гипотеза не подтверждается,
   и остаётся только пункт про схемы.

## What Changes
- Перейти на Room Gradle Plugin (`androidx.room`, есть с Room 2.6.0): `room { schemaDirectory("$projectDir/schemas") }`
  вместо аргумента KSP. Плагин передаёт каталог правильно для проверок Gradle и для кэша сборки и сам раскладывает
  экспорт по вариантам. Рекомендуется: одна правка закрывает и гонку, и up-to-date.
- Закоммитить `18.json`, `19.json`, `20.json`, сгенерированные на коммитах, где появилась каждая версия (а не из
  текущего кода, если схема версии с тех пор менялась без повышения номера).
- Отдельным изменением (зона хранилища): инструментальные тесты `MigrationTestHelper` для 17→18→19→20 и для каждой
  будущей миграции.
- Проверка: шаг 2 собирается; шаг 3 десять раз подряд без ошибки.

## Impact
- **Код:** `app/build.gradle.kts` (плагин и блок `room`), `build.gradle.kts` (объявление плагина), `app/schemas/…/18–20.json`.
- **Upstream:** `app/build.gradle.kts` и `build.gradle.kts` — существующие точки правки 2 и 1, но с новым назначением
  (плагин Room); описания в `TOUCH_POINTS` и design.md D2 нужно расширить. Новые файлы схем — в upstream-каталоге
  `app/schemas/`, вне списков: нужна новая разрешённая запись или договорённость, что схемы добавляются только новыми файлами.
- **Ядро throne, сборка, инструменты:** только сборка; `tools/diagnostics/upstream_touch_points.py` — описания точек.
- **Риски:** плагин Room проверяет, что каталог схем задан для всех вариантов; при слиянии с upstream возможен
  конфликт в `app/build.gradle.kts`. Схемы, сгенерированные не на том коммите, дадут неверную авто-миграцию.
- **Проверка исправления:** шаги 2–3; CI собирает без изменений рабочего дерева (`git status` пуст после сборки).
