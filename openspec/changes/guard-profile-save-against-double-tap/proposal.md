# Proposal

> **Категория:** надёжность · **Приоритет:** низкий ·
> **Проверка:** подтверждено по коду (окно гонки не измерялось) ·
> **Код:** upstream · **Объём:** S

## Why

### Находка

«Применить» в тулбаре редактора профиля (`R.id.action_apply`) и «Сохранить» в диалоге несохранённых изменений вызывают
один и тот же метод:

```kotlin
// app/src/main/java/io/nekohasekai/sagernet/ui/profile/ProfileSettingsActivity.kt:228-231
fun requestSave() {
    if (form?.validateAll() == false) return
    runOnDefaultDispatcher { saveAndExit() }
}
```
(вызовы — `:65` и `:413-414`). Признака «идёт сохранение» нет: каждое нажатие запускает отдельную корутину в
`GlobalScope` (`ktx/Asyncs.kt:9-10`), а `finish()` вызывается только в конце `saveAndExit()` (`:251`), после записи в БД.
Для нового профиля (`DataStore.editingId == 0`) каждая корутина выполняет
`ProfileManager.createProfile(DataStore.editingGroup, outbound)` (`:237-239`) — две вставки, два профиля.
Для существующего профиля повтор безвреден (два одинаковых `updateOutbound`).

В соседнем редакторе профиля маршрутизации такая защита есть: `RouteProfileActivity.kt:428`
(`if (model.saving) return`), `:456` (`model.saving = true`).

Окно гонки — время транзакции `createProfile` (вставка с вычислением порядка в группе) плюс время до того, как activity
перестанет принимать нажатия после `finish()`. Пока `:bg` пишет в ту же БД (обновление подписки), транзакция ждёт
блокировку — окно растёт до сотен миллисекунд, что сравнимо с интервалом двойного тапа.

### Влияние

Дубликат нового профиля в группе. Пользователь замечает его не сразу и при удалении может удалить «не тот». Если группа
участвует в автовыборе, в пул попадают два одинаковых кандидата. Редко, данные не теряются, поэтому приоритет низкий.

### Как воспроизвести

На эмуляторе не проверялось. Шаги для проверки:

1. Классический интерфейс → «+» → любой протокол → заполнить обязательные поля.
2. Дважды быстро нажать «✓»: `adb shell "input tap X Y; input tap X Y"` (координаты кнопки — из снимка экрана). Для
   надёжности параллельно запустить обновление большой подписки (сотни–тысячи серверов), чтобы транзакции `:bg` держали БД.
3. Ожидаемый неверный результат: в группе два профиля с одинаковым именем и параметрами.
4. Тест: инструментальный тест, который вызывает `requestSave()` дважды подряд на главном потоке для нового профиля, и
   проверяет, что в группе один профиль.

## What Changes

1. Флаг «идёт сохранение» в activity: выставлять в `requestSave()` на главном потоке до запуска корутины, игнорировать
   повторные вызовы, сбрасывать, если сохранение завершилось без `finish()` (например, ошибкой).
2. Дополнительно (по желанию) отключать пункт меню «Применить» на время сохранения — пользователь видит, что нажатие принято.

Как проверить: шаг 2 даёт один профиль; повторное «Применить» после ошибки сохранения снова работает.

## Impact

- **Код:** `app/src/main/java/io/nekohasekai/sagernet/ui/profile/ProfileSettingsActivity.kt` (`requestSave`, `saveAndExit`).
- **Upstream:** файл upstream вне `TOUCH_POINTS` — патч в upstream или новая точка правки (тот же файл нужен изменениям
  `keep-editor-drafts-after-process-death` и `keep-unsaved-flag-on-editor-rotation`, точку правки разумно завести одну).
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** забыть сбросить флаг на пути ошибки — тогда «Применить» перестанет работать до перезапуска экрана.
- **Проверка исправления:** инструментальный тест из шага 4; ручной сценарий из шага 2.
