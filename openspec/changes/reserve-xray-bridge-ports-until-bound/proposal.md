# Proposal

> **Категория:** надёжность · **Приоритет:** низкий (средний, если подтвердится частый перезапуск ленивого Xray) ·
> **Проверка:** гипотеза (механизм на стороне приложения подтверждён по коду) · **Код:** upstream · **Объём:** S

## Why

### Находка
Порты мостов sing-box → Xray выбираются честно, но сразу после выбора освобождаются, а Xray привязывает их позже —
при автовыборе даже лениво и, возможно, повторно после простоя. В этом окне порт может занять исходящее
loopback-соединение.

1. `LocalPorts.reserve` делает `bind(0)` на 127.0.0.1, записывает порт в таблицу аренды процесса и в `finally`
   **закрывает** все сокеты (`app/src/main/java/io/nekohasekai/sagernet/outbound/config/LocalPorts.kt:43-76`):
   ```kotlin
   } finally {
       for (socket in sockets) {
           try { socket.close() } catch (e: IOException) { }
   ```
   Аренда защищает порт только от других сборок того же процесса (KDoc `PortLease`, `LocalPorts.kt:11-16`), от ОС —
   ничем.
2. Для автовыбора все мосты резервируются одной пачкой (`ConfigGenerator.kt:942-943`) и вписываются в socks-inbound Xray и
   socks-outbound sing-box (`ChainBuilder.kt:80-98`). Другой порт ядро взять не может — он записан в конфиг.
3. При автовыборе с Xray-участниками сторона Xray стартует лениво и останавливается после простоя
   (`bg/proto/BoxInstance.kt:153-158`: `xrayLazyStart = true`, `xrayIdleSeconds = maxOf(120, autoSelector.intervalSec * 2)`).
4. Порты из `bind(0)` лежат в эфемерном диапазоне (обычно 32768–60999), откуда ядро Linux берёт исходные порты для
   исходящих TCP-соединений. На 127.0.0.1 такие соединения у приложения есть: HTTP-клиенты при включённом VPN ходят через
   mixed-порт (`ktx/Nets.kt:67`, `:156`, `:265` — подписки, rule-set'ы, гео-базы, проверка обновлений); при опции
   «HTTP-прокси» запросы других приложений идут на `127.0.0.1:mixedPort` (`ConfigGenerator.kt:705-711`); сам sing-box
   ходит на мосты Xray.

Если в момент привязки на порту `P` есть соединение с локальным адресом 127.0.0.1:P, `bind` слушающего сокета на
127.0.0.1:P в Linux получает `EADDRINUSE`: исходящий сокет без `SO_REUSEADDR` держит порт в bind-таблице.

Что неизвестно (исходников ядра в репозитории нет): привязывает ли throne-core все inbound'ы Xray при ленивом старте сразу;
что он делает при ошибке bind; как часто в обычной сессии наступает простой. Комментарий в `BoxInstance.kt:150-151`
говорит, что окно простоя выбрано больше интервала проверок, то есть при идущих проверках Xray по замыслу не засыпает.

### Влияние
Если гипотеза подтвердится: в режиме автовыбора с серверами через Xray (VLESS/Reality и т. п. — частый случай для подписок)
после очередного старта или простоя часть Xray-участников не работает. Автовыбор видит их упавшими; если упали все,
VPN «подключён», но трафик не идёт. Сбой непредсказуем и не связан с действиями пользователя.
Оценка вероятности на одну привязку: m портов мостов × k занятых loopback-портов / ≈28 000 эфемерных портов. При m = 300
и k = 2 — около 2 %, при k = 20 (много запросов через HTTP-прокси) — около 20 %. Окно есть и на обычном старте (секунды
между резервированием и запуском ядра), это поведение унаследовано от десктопной версии.

### Как воспроизвести
Шаги выведены из кода и не прогонялись.
1. В исходниках throne-core (`throneproj/Throne` по `THRONE_CORE_REF` из `nb4a.properties`) найти обработку
   `XrayLazyStart`/`xrayIdleSeconds`: когда привязываются inbound'ы и что делается при ошибке bind.
2. Проверка механизма на устройстве: открыть TCP-соединение к `127.0.0.1:<mixed-порт>`, узнать его локальный порт `P`
   (`adb shell cat /proc/net/tcp`), затем попытаться `bind`+`listen` на 127.0.0.1:P с `SO_REUSEADDR` — ожидается
   `EADDRINUSE`.
3. Стресс на эмуляторе: подписка из 50+ Xray-серверов, режим «Авто»; в `adb shell` в фоне держать сотни соединений к
   mixed-порту (цикл `toybox nc 127.0.0.1 <mixed-порт>`); дождаться простоя Xray (≥ 120 с без трафика и проверок), дать трафик.
4. Наблюдать `adb logcat | grep -iE "address already in use|xray"` и результаты проверок автовыбора: ожидаемый неверный
   результат — часть участников стабильно «упала» с ошибкой привязки.

## What Changes
- Рекомендуется: выбирать порты мостов вне эфемерного диапазона — прочитать `/proc/sys/net/ipv4/ip_local_port_range` и
  брать случайный порт ниже нижней границы (например, 10000–32767) с проверкой `bind`, сохранив таблицу аренды.
  Исходящие соединения такие порты не займут; фиксированные порты других приложений редки и отсеются проверкой.
- Вариант надёжнее, но в ядре: ядро само выбирает порт моста (`bind(0)`, держит сокет) и сообщает его стороне sing-box.
- Минимум: ядро при ошибке bind ленивого Xray сообщает ошибку так, чтобы сервис перегенерировал конфигурацию с новыми портами.
- Проверка: стресс из шага 3 — нет `EADDRINUSE`, Xray-участники отвечают после простоя.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `auto-selector`: в «Automatic node selection» уточняется — участники через Xray остаются доступными после перезапуска
  ленивого Xray; занятый порт моста не выводит участника из строя молча.

## Impact
- **Код:** `outbound/config/LocalPorts.kt` (рекомендуемый вариант); для вариантов 2–3 — ядро и `bg/proto/BoxInstance.kt`.
- **Upstream:** `LocalPorts.kt` — код upstream вне точек правки; нужна новая точка правки или патч в upstream (на десктопе
  то же окно).
- **Ядро throne, сборка, инструменты:** вариант 1 — нет; варианты 2–3 — изменение ядра.
- **Риски:** диапазон ниже эфемерного занимают известные порты других программ (2080, 7890, 10808 и т. п.) — нужна проверка
  `bind` и список исключений. Отказ от ленивого старта Xray закрыл бы окно, но вернул бы постоянный расход памяти и батареи.
- **Проверка исправления:** юнит-тест — выданные порты лежат вне `ip_local_port_range`; стресс-тест из шага 3.
