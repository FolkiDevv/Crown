# Proposal

> **Категория:** надёжность · **Приоритет:** критический · **Проверка:** воспроизведено на эмуляторе · **Код:** upstream
> (триггеры — оба) · **Объём:** M

## Why

### Находка
Любая смена сервера или настроек у работающего VPN идёт через «перезапуск на месте» `stopRunner(restart = true)`
(`bg/BaseService.kt:392`). Его вызывают `reload()`/`switchProfile()` (`BaseService.kt:292-316`), кнопки уведомления и виджеты
(`Action.SWITCH_*`, `BaseService.kt:86-88`), а также без участия пользователя: пересборка «Авто», когда все работающие участники
перестали отвечать (`AutoSelectorRuntime.kt:538-557` → `:301`, повтор с отступом 60→600 с), завершение ранжирования «Авто»
(`AutoSelectorRuntime.kt:442`), смена вердикта белых списков (`simple/regime/NetworkRegimeWatcher.kt:430,444`), обновление
подписки, заменившее работающий профиль (`SubscriptionRefresh.kt:330-332`), применение режимов и выбор сервера в simple UI.

Порядок действий при перезапуске:
1. `stopRunner` → `killProcesses()` (`BaseService.kt:464`). `VpnService.killProcesses` **первым делом закрывает TUN**, не
   различая перезапуск и окончательную остановку:
   ```kotlin
   // app/src/main/java/io/nekohasekai/sagernet/bg/VpnService.kt:48-66
   val currentConnection = conn
   …
   currentConnection?.close()
   …
   } finally { conn = null }
   super.killProcesses()            // затем закрытие старого ядра
   ```
2. Закрывается старое ядро (`proxy.close()` на `coreDispatcher`, `BaseService.kt:365`).
3. `startProxy()` (`BaseService.kt:523`) создаёт новый `ProxyInstance`: сборка конфига, при необходимости загрузка geo-файлов
   Xray и rule-set, `Mobile.newInstance`.
4. Лишь в `box.start()` ядро вызывает `openTun` → `builder.establish()` (`VpnService.kt:204`), и VPN-интерфейс появляется снова.

Между шагами 1 и 4 VPN-сети в системе нет, и Android отдаёт приложениям физическую сеть: запросы идут напрямую с реальным IP
и DNS провайдера. Платформа умеет менять интерфейс без разрыва: если `establish()` вызывается при живом интерфейсе, старый
деактивируется только после успешного создания нового, а при неудаче остаётся нетронутым. Код этим не пользуется — старый
дескриптор закрыт до нового `establish()`.

### Влияние
Каждое переключение сервера, каждое «Применить» и каждая автоматическая перезагрузка открывают окно без VPN длиной в
секунды (в худшем случае — десятки секунд, если при старте качаются geo-файлы или rule-set). Пользователь видит
«Защищено»/«Переподключение…» и об утечке не знает. Особенно неприятен случай «все серверы недоступны»: «Авто» само, в фоне,
раз в 1–10 минут открывает такое окно. В режиме «Белые списки» это нарушает требование
`simple-ui-redesign/specs/traffic-modes`, «Режим белых списков» (весь трафик MUST идти через VPN). Без always-on с
блокировкой (lockdown) защиты от этого нет.

Замеры (эмулятор Android 17, debug-сборка коммита `0a0fcc4e`, «Обход частных диапазонов» выключен). Запросы с устройства к
адресу TEST-NET `198.51.100.7:21312`, который тестовый прокси-сервер переписывает на журналирующий сервер хоста; прямая попытка
видна на хосте как исходящее соединение к `198.51.100.7`. Контроль: при выключенном VPN видна каждая попытка, при включённом
VPN в покое — ни одной.

### Как воспроизвести
1. Debug-сборка; «Расширенный режим» → «Network and TUN» → выключить «Bypass private ranges». Подписка с двумя тестовыми
   shadowsocks-серверами; на сервере правило: `198.51.100.7:21312` → журналирующий HTTP-сервер.
2. На хосте раз в 300 мс искать соединения к `198.51.100.7` (`Get-NetTCPConnection -RemoteAddress 198.51.100.7`) — любое
   найденное означает прямой выход с эмулятора.
3. Подключить «Авто»; на устройстве цикл `nc -w 3 198.51.100.7 21312` каждые 0,2–1 с.
4. а) В «Серверах» выбрать другой сервер; б) или остановить оба сервера и ждать ≈2,5 мин пересборки «Авто».
5. Наблюдать: на хосте появляются прямые соединения к `198.51.100.7`; `adb shell dumpsys connectivity` на 2–9 с теряет сеть VPN;
   в `files/core.log` — `VpnLifecycleTrace stage=tun-close` перед новым `Start:`.

## What Changes
1. **(Рекомендуется) Перезапуск без разрыва интерфейса.** При `restart = true` `VpnService.killProcesses` не закрывает старый
   `ParcelFileDescriptor`, а откладывает его. Новый `openTun` делает `establish()`; при успехе система переносит маршруты на
   новый интерфейс, после чего отложенный дескриптор закрывается. Пока новое ядро стартует, старый интерфейс остаётся
   VPN-сетью: пакеты в него никто не читает, соединения ждут или обрываются, но не уходят мимо туннеля. Если старт нового ядра
   не удался (`failRunner` → `stopRunner(false)`) или перезапуск отменён остановкой (`stopRequested`), отложенный дескриптор
   закрывается так же, как сейчас.
2. **Явное владение дескриптором.** Сейчас ядру отдаётся тот же номер fd, которым владеет `conn` (`VpnService.kt:204-206`
   `return connection.fd`). Делает ли ядро throne `dup` и закрывает ли этот номер при `close` — из Kotlin-кода не видно
   (исходников ядра в репозитории нет; известный upstream sing-box делает `dup` — для throne это предположение). Чтобы п.1 не
   зависел от этого, отдавать ядру собственную копию (`ParcelFileDescriptor.dup()` с передачей владения ядру), а оригинал
   держать в `conn`: тогда жизнь интерфейса определяет только Kotlin-сторона, и двойное закрытие одного номера исключено.
3. **Сократить окно ожидания (дополнительно).** Готовить новое ядро до закрытия старого: сборка конфига, geo-файлы, дашборд и
   `Mobile.newInstance` не требуют остановленного старого бокса; закрывать старый прямо перед `box.start()` нового. Нужна
   проверка, что `newInstance` не занимает порты слушателей.
4. **Меньше перезапусков.** Для пересборки «Авто» и смены участника — по возможности переключать участника в работающем ядре,
   без перезапуска сервиса (отдельная задача).
5. Дешёвая страховка независимо от п.1: в настройках и «Починке» предлагать «Постоянный VPN» + «Блокировать соединения без VPN».

Проверка «до/после»: тот же стенд, 20 переключений сервера и 5 пересборок «Авто» — 0 прямых соединений к `198.51.100.7`, сеть VPN
в `dumpsys connectivity` не пропадает; остановка VPN по-прежнему снимает интерфейс; неудачный старт нового ядра не оставляет
«VPN есть, интернета нет».

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `proxy-connection`: «Connection state machine» — новое требование «Переключение профиля или перезагрузка работающего VPN не
  выпускает трафик мимо туннеля: VPN-интерфейс заменяется новым без промежутка, а снимается только при окончательной остановке
  или неудачном старте».
- `simple-ui-redesign/specs/traffic-modes`: «Режим белых списков» опирается на это требование при смене режима и сервера.

## Impact
- **Код:** `bg/VpnService.kt` (`killProcesses`, `openTun`), `bg/BaseService.kt` (`stopRunner`, `startProxy`, ветки отмены и
  ошибки), `moe/matsuri/nb4a/NativeInterface.kt:59-61` (передача fd ядру).
- **Upstream:** `VpnService.kt` и `NativeInterface.kt` (точка 8 описывает другое) — нужна новая точка правки или патч в upstream
  (проблема общая). `BaseService.kt` — существующая точка 6, описание нужно расширить.
- **Ядро throne:** поведение ядра с fd TUN нужно проверить (п.2 снимает зависимость); сборка не затрагивается.
- **Риски:** при ошибке нового старта старый дескриптор обязан закрыться, иначе останется интерфейс без ядра; гонка с
  `stopRequested` в `stopRunner`; смена набора приложений (allow/deny) создаёт на стороне системы новую VPN-сеть — проверить,
  что и тогда старая снимается после новой. Смена режима VPN → прокси идёт не через restart и не меняется.
- **Проверка исправления:** стенд выше на Android 10, 14, 17; ручной тест «неудачный старт нового ядра» (недоступный geo-файл).
- **Внешние источники:**
  - `VpnService.Builder.establish()`: «the old interface will be deactivated when the new one is created successfully. If the
    new interface cannot be created, the existing interface and its file descriptor remain untouched» —
    https://developer.android.com/reference/android/net/VpnService.Builder#establish()
  - `VpnService` («The existing interface is deactivated when a new one is created»):
    https://developer.android.com/reference/android/net/VpnService
