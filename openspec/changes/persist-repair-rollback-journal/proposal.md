# Proposal

> **Категория:** надёжность · **Приоритет:** средний · **Проверка:** воспроизведено на эмуляторе · **Код:** Crown ·
> **Объём:** S–M

## Why

### Находка
Каждое пробное исправление «Починки» сразу пишет настройку в общую БД (`simple/repair/DeviceRepairFixes.kt:189-235`,
`setting(...)`: `DataStore.directDns`, `remoteDns`, `vpnMtu`, `selectedProxy`), затем VPN перезагружается и выполняется
повторная проверка — до `FIX_TIMEOUT_MS = 120 000` мс (`RepairEngine.kt:251`). Вернуть прежнее значение, если исправление не
помогло, может только объект в памяти UI-процесса:

```kotlin
// app/src/simple/java/io/nekohasekai/sagernet/simple/repair/RepairViewModel.kt:156
val journal = RepairJournal(...)
// RepairViewModel.kt:388-389
/** One carry for the process: the chain rule of a setting holds across runs. */
val unrestored = UnrestoredChanges(::inSettingsTransaction, ::restoreFailed, ::superseded)
```

`RepairJournal` хранит записи в `ArrayList` (`RepairFixes.kt:69`, `:114`), `UnrestoredChanges` («повторить откат позже») — тоже
в памяти (`RepairFixes.kt:273`). Откат по неудачной повторной проверке, по «Остановить» (`RepairEngine.kt:106-140`) и при
`onCleared` выполняется, только пока жив UI-процесс. На диске нет отметки, что значение пробное, поэтому новый процесс ничего
не откатывает.

UI-процесс может умереть в этом окне в обычных ситуациях: пользователь свернул приложение во время долгого шага, и система
выгрузила процесс (у него нет foreground-сервиса — VPN живёт в `:bg`); пользователь смахнул задачу из «Недавних», потому что
«Починка» идёт долго; падение процесса.

### Влияние
Пробное значение остаётся навсегда и молча: MTU 1280 вместо значения пользователя, другой удалённый DNS, прямой DNS из
белого списка или другой выбранный сервер. Экран «Починки» в новом процессе пуст; о том, что настройка изменена, нигде не
сказано. Хуже того, следующая «Починка» считает оставшееся значение исходным и откатывает уже к нему — исходное значение
пользователя теряется. Это нарушает connection-repair «Откат неудачного исправления» и сценарий «Остановка» требования
«Запуск «Починки»».

Окно уязвимости — всё время повторной проверки: на эмуляторе от применения исправления до отката прошло 16 с.

### Как воспроизвести
Эмулятор Android 17, debug-сборка `0a0fcc4e`, простой интерфейс, «Авто» над двумя локальными серверами shadowsocks; на серверах
(sing-box) правило `reject` для адресов публичных DNS (`8.8.8.8`, `1.1.1.1`, …) и портов 53/853 — DNS через VPN не отвечает
ни с исходным, ни с альтернативным удалённым DNS, а URL-тест серверов проходит. Журнал уровня info.
1. Удалённый DNS по умолчанию (`https://8.8.8.8/dns-query`). Запустить «Починку».
2. Сразу после строки
   `simple repair: fix vpn_dns_alternative: remote DNS 'https://8.8.8.8/dns-query' -> 'https://1.1.1.1/dns-query'`
   убить UI-процесс (`run-as dev.folki.crown.debug kill -9 <pid UI>`; на эмуляторе — через 0,03 с после строки).
3. Открыть приложение снова. Фактически: в настройках `remote_dns = https://1.1.1.1/dns-query`, строки `rollback` нет.
4. Контроль — тот же прогон без убийства процесса:
   ```
   05:22:03 fix vpn_dns_alternative: remote DNS 'https://1.1.1.1/dns-query' -> 'https://8.8.8.8/dns-query'
   05:22:19 dns_vpn -> fail vpn_dns_no_answer
   05:22:19 rollback vpn_dns_alternative: remote DNS back to 'https://1.1.1.1/dns-query'
   ```
   Откат работает, но к значению, оставшемуся от прерванного прогона: исходное `8.8.8.8` потеряно.

## What Changes
1. (рекомендуется) Сохранять журнал отката на диске до применения исправления: запись «настройка, значение до, значение после,
   сеанс процесса» в отдельном ключе (например, `simple_repair_journal`) в той же транзакции настроек, что и само исправление
   (`RepairLog.inSettingsTransaction` уже есть). Запись удаляется после удачной повторной проверки (исправление остаётся) или
   после отката. При следующем старте простого интерфейса записи чужого сеанса откатываются по уже реализованному правилу
   «только если в настройке всё ещё наше значение» (compare-and-set). Готовый образец — `PendingImports` с сеансом процесса и
   `heal` (`simple/add/PendingImports.kt`, `SimpleImport.healInterrupted`).
2. То же для `UnrestoredChanges`: незавершённые откаты хранить в том же ключе, а не в памяти процесса.
3. Запуск VPN «Починкой» для проверок (`DeviceRepairChecks.kt:491-515`) при восстановлении не повторять и не откатывать —
   только записать в журнал.
4. Дешёвая частичная мера: при следующем открытии «Починки» показывать «Прерванная проверка изменила <настройка>, вернуть?».

Проверка: сценарий выше — после повторного открытия приложения `remote_dns` снова `https://8.8.8.8/dns-query`, в журнале строка
отката с пометкой «после прерванного прогона»; контрольный прогон не меняется.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `connection-repair` (simple-ui-redesign): «Откат неудачного исправления» и «Запуск «Починки»» (сценарий «Остановка») —
  откат MUST выполняться и тогда, когда процесс приложения завершился до окончания проверки: при следующем запуске
  незавершённые пробные изменения возвращаются, если в настройке осталось записанное «Починкой» значение.

## Impact
- **Код:** `simple/repair/RepairFixes.kt` (`RepairJournal`, `UnrestoredChanges`), `simple/repair/RepairViewModel.kt`
  (`RepairLog`), `simple/repair/RepairEngine.kt`, точка восстановления при старте простого интерфейса
  (`simple/SimpleActivity.kt` или `SimpleHooks`).
- **Upstream:** код Crown.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** откат после перезапуска не должен затирать значение, которое пользователь успел сменить сам (compare-and-set,
  как `stillApplied`); исправление, которое помогло, не должно откатываться — запись удаляется сразу после удачной проверки.
  «Починка» и откат работают в UI-процессе, а `:bg` читает настройки только при перезагрузке, поэтому откат после перезапуска
  должен сопровождаться перезагрузкой работающего VPN (с учётом `make-service-state-reliable-across-processes`).
- **Проверка исправления:** сценарий выше (с убийством процесса и контролем); инструментальный тест с `kill` процесса между
  применением и повторной проверкой — JVM-тест над `RepairJournal` этого не ловит.
