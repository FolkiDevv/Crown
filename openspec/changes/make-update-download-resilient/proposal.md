# Proposal

> **Категория:** надёжность · **Приоритет:** средний · **Проверка:** подтверждено по коду (отсутствие защиты и докачки);
> замирание в фоне — гипотеза, зависит от устройства · **Код:** upstream · **Объём:** M

## Why

### Находка
Загрузка APK самообновления идёт в корутине главного процесса без foreground-сервиса и без WorkManager:

```kotlin
// app/src/main/java/io/nekohasekai/sagernet/update/UpdateManager.kt:53
private val scope = CoroutineScope(SupervisorJob() + Dispatchers.IO)

// UpdateManager.kt:142-145 (fetch)
val part = File(dir, expected.name + ".part")
part.delete()
val request = Request.Builder().url(offer.apk!!.url).header("User-Agent", USER_AGENT).build()
val httpCall = UpdateChecker.httpClient(timeoutSeconds = 60).newCall(request)
```

- Процесс ничем не защищён: прогресс живёт в памяти (`_state`), уведомление с прогрессом процесс не удерживает.
- Докачки нет: `.part` удаляется перед каждой попыткой, заголовок `Range` не отправляется.
- При каждом старте главного процесса каталог загрузки удаляется целиком (`UpdateManager.kt:70-72`, `onAppStart`).
- Окно обновления само предлагает увести загрузку в фон: в состоянии «Загрузка» есть кнопки «Отмена» и «Скрыть», и
  «Скрыть» просто закрывает окно (`update/UpdateActivity.kt:124-127`). После этого у главного процесса нет ни видимой
  activity, ни сервиса, и он становится кэшированным. Привязка к VPN-сервису в `:bg` это не меняет: привязка повышает
  приоритет сервиса, а не клиента.

APK текущей release-сборки весит около 48–50 МБ. На медленном или замедленном DPI канале загрузка идёт минуты.

Что тогда делает платформа:
- при нехватке памяти система первым убивает кэшированный процесс. Загрузка пропадает молча; висящее уведомление
  прогресса остаётся до следующего запуска, а при следующем запуске `.part` удаляется и всё начинается с нуля;
- на устройствах, где включена заморозка кэшированных приложений, процесс замораживается через 10 с после перехода в
  кэш (Android 14+). Поток загрузки останавливается; после разморозки соединение, скорее всего, уже закрыто сервером —
  ошибка и уведомление «Не удалось обновить». Документация AOSP прямо говорит, что кэшированные процессы не должны
  выполнять работу.

Для сравнения: обновления подписок в `:bg` на время ручных задач держат сервис в foreground (`CoreForeground.acquire`,
`group/SubscriptionQueue.kt:325`).

### Влияние
Самообновление — основной канал доставки исправлений Crown. На медленной сети, если пользователь не сидит на экране
загрузки, оно срывается или начинается заново, и каждая повторная попытка снова тянет около 50 МБ — заметный расход
мобильного трафика. Хранилище ассетов GitHub поддерживает докачку (проверено: запрос с `Range` получает `206 Partial
Content`), так что потерянный трафик можно не терять.

### Как воспроизвести
Шаги выведены из кода и документации, не прогонялись.
1. Опубликованный выпуск новее установленного (или локальная подмена ответа). Ограничить скорость эмулятора:
   `adb emu network speed edge`.
2. «Проверить обновления» → «Обновить», во время загрузки нажать «Скрыть», затем «Домой».
3. Через 30–60 с: `adb shell dumpsys activity processes | grep -A3 dev.folki.crown.debug` — состояние процесса
   (кэшированный, frozen); `adb shell run-as dev.folki.crown.debug ls -l no_backup/update/` — растёт ли `.part`.
   Для проверки заморозки на эмуляторе: `adb shell settings put global cached_apps_freezer enabled` и перезагрузка.
4. Ожидаемый неверный результат: `.part` перестаёт расти, затем «Не удалось обновить» или вечное уведомление прогресса.
5. `adb shell am kill dev.folki.crown.debug`, снова «Обновить» — загрузка начинается с 0 байт.

## What Changes
- Рекомендуется: выполнять загрузку под защитой процесса — либо `CoroutineWorker` с `setForeground` (долгая работа
  WorkManager), либо в собственном foreground-сервисе типа `dataSync`. Прогресс по-прежнему отдавать через `StateFlow` и
  уведомление. На Android 15+ учитывать бюджет `dataSync` (`onTimeout`): при исчерпании — пауза и продолжение позже.
- Докачка: не удалять `.part`, а продолжать с `Range: bytes=<размер>-`; при ответе `206` дописывать, при `200` — начинать
  сначала. Целостность остаётся под защитой проверки SHA-256 и подписи (`UpdateVerifier.verify`).
- `onAppStart`: удалять только завершённые и чужие файлы, а `.part` текущего предложения сохранять (сверять имя и размер
  с манифестом при следующей проверке).
- Частичная мера без нового сервиса: только докачка и сохранение `.part`. Повтор тогда не тратит трафик, но замирание
  в фоне остаётся.
- Проверка: сценарий выше — после «Скрыть» и «Домой» `.part` растёт; после убийства процесса загрузка продолжается
  с места обрыва (в журнале запрос с `Range`, ответ `206`).

## Impact
- **Код:** `update/UpdateManager.kt`, `update/UpdateActivity.kt` (подпись кнопки «Скрыть» может остаться), новый воркер
  или сервис; `AndroidManifest.xml` — объявление сервиса или `SystemForegroundService` с типом `dataSync`.
- **Upstream:** `UpdateManager.kt` — код upstream вне списков: нужна новая точка правки или патч в upstream. Манифест —
  существующая точка 3, но с новым назначением (описание расширить).
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** foreground-сервис требует разрешения `FOREGROUND_SERVICE_DATA_SYNC` (уже объявлено) и показывает уведомление
  (оно и так есть). Неверная докачка может склеить разные версии файла — защищает проверка размера и SHA-256, при
  несовпадении `.part` удалять.
- **Проверка исправления:** шаги 2–5 до и после; тест докачки с MockWebServer (ответ `206` на `Range`).

  - Foreground service timeouts (dataSync, Android 15): https://developer.android.com/develop/background-work/services/fgs/timeout
