# Proposal

> **Категория:** скорость · **Приоритет:** средний · **Проверка:** воспроизведено на эмуляторе (трасса подключения) ·
> **Код:** upstream · **Объём:** M

## Why

### Находка
Режим «Авто» в simple — автовыбор с параметрами по умолчанию над всеми подписками
(`app/src/simple/java/io/nekohasekai/sagernet/simple/modes/TrafficModes.kt:273-279`): `buildLimit = 300`, `poolCap = 1000`
(`app/src/main/java/io/nekohasekai/sagernet/outbound/types/AutoSelector.kt:35-36`). Это основной путь «Подключить» в
simple. При каждом старте и каждом reload такого профиля процесс `:bg` трижды собирает каждого из 300 участников и
каждого отдельно проверяет ядром:

1. **Структурная проверка.** `ConfigGenerator.rejectedMembers` (`outbound/config/ConfigGenerator.kt:1053-1066`) для
   каждого id вызывает `chains.candidateError(listOf(id))` — это `buildXray`/`buildChecked` участника
   (`outbound/config/ChainBuilder.kt:272-289`).
2. **Проверка ядром.** Для прошедших — `CoreMemberCheck.rejected` (`database/SettingsMapper.kt:213-266`, подключается
   только в `:bg`, `SettingsMapper.kt:42`, `:49`): участник собирается ещё раз и проверяется отдельным конфигом ядра,
   в пуле потоков, который создаётся заново на каждый вызов:
   ```kotlin
   // SettingsMapper.kt:217-219
   val pool = Executors.newFixedThreadPool(minOf(10, members.size))
   val verdicts = members.map { (_, outbound) -> pool.submit(Callable { coreError(outbound, ctx, logLevel) }) }
   ```
   `coreError` вызывает `Mobile.checkConfig(...)` или `Mobile.checkXrayConfig(...)` (`SettingsMapper.kt:236-260`).
3. **Сборка.** При построении цепочки участника — третий `buildChecked` (`ChainBuilder.kt:439`).

Вердикты между генерациями не сохраняются (`CoreMemberCheck` — объект без состояния), хотя участники от старта к старту
почти не меняются: подписка обновляется раз в часы, а переподключение (смена сети, reload после правки настроек,
авто-переподключение) случается чаще. Старт VPN всё это время ждёт: генерация идёт в потоке `CoreLifecycle`.

### Влияние
Замер на эмуляторе Android 17, release-сборка, режим «Авто» по подписке из 3000 shadowsocks-серверов на локальном
сервере, трасса `atrace` одного подключения: пул проверки участников (потоки `pool-N-thread-1…10`, созданы из
`CoreLifecycle`) живёт **1,18 с** и тратит **0,58 с** CPU. В той же серии время «нажатие → `Established … on tun0`»:
медиана 6,0 с для «Авто»/3000 против 3,1 с для одного сервера. Значит, проверка участников ядром — около трети
добавки режима «Авто», и она повторяется на каждом reload. Эмулятор работает на быстром x86-хосте; на телефоне средней
мощности время ожидаемо больше. Кроме времени — CPU и батарея на каждом переподключении. Обещания о времени старта в
спецификациях нет; поведение автовыбора (`auto-selector`) не меняется.

Отдельная, но соседняя проблема — построчные SQL-запросы при той же генерации (профили по одному `getById`,
`bg/proto/CoreConfigs.kt:35`); её решение независимо от этого.

### Как воспроизвести
Числа выше получены по шагам 1–4; шаг 5 (повторный reload) выведен из кода и не прогонялся.
1. Release-сборка, simple UI, подписка на 3000 серверов (или 300+ серверов в одной группе), режим «Авто», VPN выключен.
2. `adb shell "atrace --async_start -b 32000 -c am dalvik sched database"`.
3. «Подключить»; дождаться в logcat `Vpn: Established by dev.folki.crown on tun0`.
4. `adb shell "atrace --async_stop -b 32000 -c am dalvik sched database" > t.txt`; в `t.txt` найти потоки
   `pool-N-thread-1…10` процесса `:bg` — время от первого до последнего события и сумма интервалов `sched_switch`.
5. Переподключиться без изменения подписки (выключить и включить Wi-Fi или сменить настройку, требующую reload): пул
   снова живёт столько же — проверка повторяется для тех же участников.

## What Changes
- Рекомендуется: кэш вердиктов проверки ядром в памяти `:bg`. Ключ — компактный JSON собранного участника (результат
  `buildChecked`/`buildXray`) и уровень логов; значение — ошибка или «годен». Ограниченный размер (LRU на несколько тысяч
  записей). Ядром проверяются только новые или изменившиеся участники. Смена `ThroneCore` означает новый процесс, кэш
  сбрасывается сам. Ключ из собранного JSON автоматически учитывает глобальные настройки, влияющие на сборку.
- Не собирать участника трижды: результат сборки из `candidateError` передавать в `CoreMemberCheck` и в построение цепочки.
  Осторожно с `Custom.bridgePort`, который назначается при сборке (`ChainBuilder.kt:331-332`).
- Пул потоков проверки создавать один раз на процесс, а не на каждый вызов (мелочь рядом с кэшем).
- Проверка: та же трасса — на повторном подключении с той же подпиской пул проверки не появляется или живёт десятки мс;
  медиана «нажатие → Established» для «Авто»/3000 по 10 повторам падает примерно на 1 с на эмуляторе.

## Impact
- **Код:** `database/SettingsMapper.kt` (`CoreMemberCheck`), `outbound/config/ConfigGenerator.kt` (`rejectedMembers`),
  `outbound/config/ChainBuilder.kt`.
- **Upstream:** код upstream, точек правки форка в этих файлах нет — нужна новая точка правки (например,
  `SettingsMapper.kt`: «кэш проверки участников автовыбора») или патч в upstream, где тот же недостаток.
- **Ядро throne, сборка, инструменты:** ядро не меняется, только реже вызывается его проверка.
- **Риски:** ключ кэша, не покрывающий что-то из собранного JSON, пропустит участника, которого ядро отвергнет, а один
  такой участник валит старт всей группы (`ConfigGenerator.kt:911`). Поэтому ключ — именно собранный JSON, а не id профиля.
  Частичная мера без кэша — уменьшить `buildLimit` управляемого селектора simple (решение продукта: меняет, сколько
  серверов пробует автовыбор).
- **Проверка исправления:** трасса из «Как воспроизвести» до и после; юнит-тест на кэш — изменение поля участника меняет ключ.
- **Внешние источники:** нет.
