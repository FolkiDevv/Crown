# Proposal

> **Категория:** надёжность · **Приоритет:** низкий · **Проверка:** гипотеза (логический пробел подтверждён по коду,
> гонка не воспроизведена) · **Код:** Crown · **Объём:** S

## Why

### Находка
Раздел «Серверы» запускает фоновый раунд проверок: URL-тест, затем проверку IP выхода. На время раунда он ставит
`ownTest` и `roundBusy` (`app/src/simple/java/io/nekohasekai/sagernet/simple/servers/ServersViewModel.kt:563-571`). Снимает
их только тогда, когда увидит итог своей сессии в `TestSessionClient.state`:

```kotlin
// ServersViewModel.kt:640-655 (сокращено)
if (ownTest == NONE || test === stateBeforeTest) return
if (test.kind != ownTest) {
    if (test.running) { ownTest = NONE; roundBusy = false; ... }   // идёт чужая сессия
    return                                                          // не идёт и не наша — пропуск
}
...
if (test.running) return
val finished = ownTest; ownTest = NONE                              // конец раунда
```

Свою сессию ViewModel узнаёт только по виду (`kind`). Состояние «сессий нет» (`TestUiState()`, `kind = -1`,
`running = false`) при взведённом `ownTest` попадает в ветку «пропуск», и раунд остаётся «идущим» навсегда.

Такое состояние можно увидеть вместо своего итога, потому что `state` — это `StateFlow`
(`ui/test/TestSessionClient.kt:48`): сборщик видит только последнее значение. Тот же поток читает «Починка».
`DeviceRepairChecks.urlTest` (`simple/repair/DeviceRepairChecks.kt:437-455`) ждёт `!running`, сразу начинает свою сессию
того же вида `KIND_URL` и в `finally` вызывает `dismiss()`, который ставит `TestUiState()` (`TestSessionClient.kt:158-165`).
Оба сборщика работают в главном потоке. Если на конце раунда «Серверов» первым возобновится сборщик «Починки»,
«Серверы» увидят уже сессию «Починки» (`KIND_URL`, `running`) и примут её за свою. В конце сессии «Починки» они могут
увидеть уже `TestUiState()` после её `dismiss()`.

Обратный порядок даёт другой сбой. «Серверы» считают итог сессии «Починки» своим и сами вызывают `dismiss()`
(`ServersViewModel.kt:668`). «Починка» тогда читает пустой `TestUiState()`, и все серверы для неё «без ответа».

### Влияние
Если гонка срабатывает:
- в «Серверах» строки остаются в состоянии «Страна определяется…», новые фоновые раунды не начинаются, ручная
  «Проверить задержку» отвечает «проверка уже идёт» (`ServersViewModel.kt:380-383`). Так продолжается, пока не
  пересоздастся экран или не начнётся новая сессия того же вида;
- либо шаг «Доступность серверов» в «Починке» получает пустой результат и считает все серверы недоступными.

Для гонки нужен запуск «Починки» во время фонового раунда «Серверов». Типично это двухпанельная раскладка (планшет, ТВ)
или «Починка» с баннера главной сразу после открытия «Серверов». Обычно сборщик «Серверов» живёт дольше и
возобновляется первым, поэтому сбой ожидается редким. Это не подтверждено прогоном.

### Как воспроизвести
Не прогонялось. Надёжнее всего проверить JVM-тестом:
1. Тест `ServersViewModel` (или его логики раунда) с подменённым потоком состояний тестов.
2. Взвести раунд (`startUrlTest` с успешным `startProfiles`), затем подать в обработчик подряд: `running KIND_URL` →
   `TestUiState()` (без итога `KIND_URL, running = false`).
3. Ожидаемо неверно: `roundBusy == true` и `ownTest == KIND_URL` после последнего значения. Следующий `startUrlTest`
   ничего не запускает.

На устройстве (вероятностно): планшетный эмулятор, подписка на ~100 серверов (часть без страны в имени), главная и
«Серверы» рядом. Открыть «Серверы» и сразу запустить «Починку». После неё в меню сервера выбрать «Проверить задержку».
Неверный результат: снекбар «проверка уже идёт» и вечное «Страна определяется…». Повторить 10–20 раз.

## What Changes
1. **Рекомендуется (код Crown):** считать раунд оконченным, когда приходит любое состояние с `!running`, если раунд
   взведён и это не `stateBeforeTest`, включая `kind < 0`. Тогда список перечитывается, `ownTest`/`roundBusy`
   снимаются, ставится `startQueued()`. Результаты своей сессии `:bg` уже сохранил в БД, следующее чтение их подхватит.
2. Не принимать чужую сессию за свою. Запоминать идентичность сессии (`TestUiState.session`, когда он стал ненулевым)
   из первого своего состояния `running` и сравнивать с ней. В «Серверах» не вызывать `dismiss()`, если итог — не их
   сессии. Надёжный вариант — `TestSessionClient.startProfiles` возвращает токен сессии. Это правка файла вне точек
   правки, поэтому он вторым.
3. Страховка: таймаут раунда (например, 2× таймаут теста × число партий). По его истечении раунд снимается.

Как проверить: JVM-тест из раздела выше проходит. Ручной сценарий 10–20 раз не даёт зависания. «Починка» получает
задержки своих серверов, а не пустой результат.

## Impact
- **Код:** `app/src/simple/java/io/nekohasekai/sagernet/simple/servers/ServersViewModel.kt`; для п. 2 надёжного варианта —
  `app/src/main/java/io/nekohasekai/sagernet/ui/test/TestSessionClient.kt`.
- **Upstream:** пп. 1 и 3 — код Crown. Токен сессии из п. 2 требует новой точки правки в `TestSessionClient.kt`.
- **Ядро throne, сборка, инструменты:** не затрагиваются.
- **Риски:** раунд, снятый раньше времени, может запустить следующий тест, пока `:bg` ещё занят. `startProfiles` тогда
  вернёт `false`, и раунд будет пропущен. Это то же поведение, что и сейчас при чужой сессии.
- **Проверка исправления:** новый JVM-тест логики раунда; ручной сценарий «Серверы» + «Починка».
