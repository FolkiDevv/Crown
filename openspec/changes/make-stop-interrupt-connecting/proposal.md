# Proposal

> **Категория:** надёжность, скорость · **Приоритет:** средний · **Проверка:** подтверждено по коду (длительность старта
> ядра — гипотеза) · **Код:** upstream (точка правки `BaseService.kt`) и ядро · **Объём:** M

## Why

### Находка
Старт и закрытие ядра выполняются на одном потоке `CoreLifecycle`
(`app/src/main/java/io/nekohasekai/sagernet/bg/BaseService.kt:50`), чтобы закрытие не пересекалось со стартом. Подключение
идёт в `connectingJob` на `Dispatchers.Main`:
```kotlin
// BaseService.kt:676-684 (сокращено)
data.connectingJob = CoroutineScope(Dispatchers.Main).launch {
    preInit()
    withContext(coreDispatcher) { proxy.init() }      // сборка конфигурации и Mobile.newInstance — блокирующий JNI
    ...
    withContext(coreDispatcher) { startProcesses() }  // box.start() — блокирующий JNI (BoxInstance.kt:113-115)
```
«Стоп» (`stopRunner`) переводит состояние в `Stopping` (`BaseService.kt:420`) и сначала отменяет подключение и ждёт его:
`data.connectingJob?.cancelAndJoin() // ensure stop connecting first` (`:438-443`). Отмена корутины не прерывает поток,
занятый вызовом в Go: `cancelAndJoin` ждёт, пока `Mobile.newInstance` (`bg/proto/BoxInstance.kt:67-69`) или `box.start()`
вернутся сами. Закрыть экземпляр, чтобы прервать старт, тоже нельзя: `killProcesses()` → `withContext(coreDispatcher) {
proxy.close() }` (`BaseService.kt:365`) стоит в той же однопоточной очереди за стартом.

Когда старт долгий: по умолчанию старт ждёт удалённые наборы правил (`deferRuleSets = false`, `BoxInstance.kt:37`; без
ожидания — только после согласия пользователя, `BaseService.kt:625`). KDoc `bg/proto/DeferredRuleSets.kt:19-22`: ядро при
старте роутера скачивает каждый удалённый rule-set без кэша, и неудача одного валит весь старт. Сколько длится такая
загрузка, определяют тайм-ауты ядра; из Kotlin это не видно. Другие долгие случаи — большой автовыбор (секунды на сборку и
проверку участников) и медленное устройство.

### Влияние
Пользователь нажимает «Подключить», видит долгое «Подключение» (плохая сеть, недоступен хост наборов правил), нажимает
«Стоп» — на экране «Остановка», и она длится столько, сколько длился бы старт; повторные нажатия игнорируются, пока
состояние `Stopping`. Если старт в итоге удался, ядро успевает открыть TUN и сразу закрывается — лишнее мигание VPN.
Выбор другого сервера в это время ждёт так же. Обычный старт на эмуляторе — 1,6–9,9 с от нажатия до установленного VPN;
«Стоп» ждёт остаток. Насколько долго старт висит при недоступных наборах правил — не измерено.

### Как воспроизвести
Шаги выведены из кода и не прогонялись.
1. Профиль маршрутизации с удалённым rule-set; кэш наборов очищен (очистка данных приложения или новая установка).
2. Сделать хост набора недоступным без явного отказа: подменить URL набора на адрес из TEST-NET (`192.0.2.1`) или на
   локальный HTTP-сервер (`adb reverse`), который принимает соединение и не отвечает.
3. «Подключить», через 2 с — «Стоп».
4. В logcat засечь время от `ServiceStopTrace ... state=Connecting` до `ServiceLifecycleTrace ... stage=kill done`. Ожидаемый
   неверный результат: оно равно времени до ошибки старта ядра (секунды–десятки секунд), всё это время на экране «Остановка».
5. Сравнить с профилем без удалённых наборов: «Стоп» срабатывает за доли секунды после завершения старта.

## What Changes
- Рекомендуется (нужна проверка ядра): при отмене подключения во время `box.start()` прерывать старт из другого потока —
  отменой контекста старта или закрытием экземпляра в обход очереди `CoreLifecycle`, если ядро это допускает. Тогда загрузки
  наборов правил прервутся, и `box.start()` быстро вернётся с ошибкой отмены. Для этого ядру, возможно, нужен отдельный
  метод «прервать старт».
- Альтернатива только в Kotlin: ограничить ожидание в `stopRunner` коротким сроком (например, 3–5 с). Если старт
  вернулся раньше — закрыть ядро с флагом «закрыть сразу после старта» (поздний удачный старт не должен объявлять
  «Подключено») и показать «Остановлено». Если срок истёк — завершить процесс `:bg` и только после этого показать
  «Остановлено»: до подтверждённого закрытия ядра или смерти процесса состояние остаётся «Останавливается», иначе поздний
  старт открыл бы TUN уже после «Остановлено». Следующий старт идёт в новом процессе, очередь и TUN свободны. Цена —
  холодный старт `:bg` при следующем подключении; без отмены старта в ядре это полумера.
- Частично: срок на загрузку наборов правил при старте (если ядро даёт такую опцию).
- Проверка: сценарий выше — время от «Стоп» до «Остановлено» при недоступных наборах правил: < 1–3 с с отменой в ядре,
  не больше срока ожидания (3–5 с) плюс завершение `:bg` в альтернативе.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `proxy-connection`: в «Connection state machine» добавляется — остановка во время подключения завершается за
  ограниченное время и не ждёт окончания блокирующего старта ядра.

## Impact
- **Код:** `bg/BaseService.kt` (`stopRunner`, `connectingJob`), `bg/proto/BoxInstance.kt`; возможно — API ядра.
- **Upstream:** `BaseService.kt` — существующая точка правки 6 («SimpleHooks service start/stop»), её описание нужно
  расширить; `BoxInstance.kt` — новая точка правки или патч в upstream.
- **Ядро throne, сборка, инструменты:** рекомендуемый вариант затрагивает ядро (прерывание старта); альтернатива — нет.
- **Риски:** закрытие во время старта — гонка внутри ядра; без подтверждения поведения ядра безопаснее альтернатива.
  В альтернативе «Остановлено» появляется позже (до 3–5 с), а следующее подключение платит холодным стартом `:bg`.
- **Проверка исправления:** сценарий «Как воспроизвести»; повторные «Подключить»/«Стоп» подряд не оставляют два экземпляра
  ядра и два TUN.
- **Внешние источники:**
  - kotlinx.coroutines, отмена кооперативна и не прерывает блокирующий код: https://kotlinlang.org/docs/cancellation-and-timeouts.html
