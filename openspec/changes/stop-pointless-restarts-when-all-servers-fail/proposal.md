# Proposal

> **Категория:** надёжность, скорость · **Приоритет:** средний · **Проверка:** воспроизведено на эмуляторе ·
> **Код:** upstream · **Объём:** S

## Why

### Находка
Монитор автовыбора в `:bg` опрашивает ядро раз в 2 с (10 с при выключенном экране) и считает пул «исчерпанным», когда ни
один участник не годен, ядро не приостановлено и устройство не в Doze:

```kotlin
// app/src/main/java/io/nekohasekai/sagernet/bg/autoselector/AutoSelectorRuntime.kt:532-535
val usable = sample.members.count { it.isUsable || it.state == AutoSelectorStatus.STATE_UNTESTED || it.isSuspect }
val everythingDead = usable == 0 && sample.membersProbed > 0 && !sample.suspended && !idle &&
    sample.phase != "starting"
```

Через 20 с такого состояния (`EXHAUSTED_GRACE_MS`, `:48`) и с паузой 60 → 120 → 240 → 480 → 600 с (`:49-50`, `:541-546`)
вызывается `onExhausted` (`:338-362`). Сеть он проверяет только как «у Android вообще нет сети»
(`SagerNet.underlyingNetwork == null`). Дальше `rebuild(run, stale = lastBuilt)` (`:290-304`) URL-тестирует
неизмеренных участников и всех участников последней сборки, а затем **безусловно** перезапускает ядро на месте:

```kotlin
// AutoSelectorRuntime.kt:298-302
if (ranked) measure(run.service, profileId, id, stale.orEmpty())
if (claim() && current() === run && run.service.data.state.canStop) {
    if (ranked) synchronized(lock) { rankedFor = profileId }
    run.service.stopRunner(true)
}
```

Перезапуск ничего не меняет, если других серверов нет. В обычном «Авто» простого интерфейса пул не больше лимита сборки
(`buildLimit = 300`): в сборку уже входят все участники, а когда все свежие результаты провальные, планировщик намеренно
оставляет их всех (`outbound/config/AutoSelectorPlan.kt:462-465`: «Every member's last test failing is an outage … excluding
them all would leave nothing»). Новая сборка совпадает со старой. Для автовыбора «за цепочкой» такая проверка уже есть —
`AutoSelectorProfiles.demoteLastBuilt` возвращает false, если `plan.pool.size <= plan.build.size`
(`bg/autoselector/AutoSelectorProfiles.kt:85-88`), — для обычного её нет.

«Все не отвечают при живой сети» — типовая ситуация пользователей Crown: зона белых списков мобильного интернета, блокировка
протокола у провайдера связи, сбой у провайдера VPN, Wi-Fi с порталом авторизации.

### Влияние
Пока сбой длится (минуты — часы), через 1, 2, 4, 8, затем каждые 10 минут:
- URL-тест участников последней сборки (до 300 серверов) — сокеты, CPU и пробуждения `:bg`, в том числе при выключенном
  экране вне Doze; на это время занят тестовый движок (ручные тесты и «Починка» получают «занято»);
- перезапуск ядра на месте: обрыв всех соединений, «Переключение…» в уведомлении и окно, в котором TUN уже закрыт, а новый
  ещё не создан — трафик идёт мимо VPN (механизм и решение — `keep-tunnel-during-in-place-restart`). На эмуляторе одно окно
  длилось 4–9 с, за него было 4 и 6 прямых соединений;
- каждый перезапуск — шанс не стартовать вовсе (ошибка сборки конфигурации, загрузка наборов правил).

Восстановление при этом не ускоряется: ядро и без перезапуска продолжает пробовать участников и само переключится на сервер,
когда тот оживёт.

### Как воспроизвести
Эмулятор Android 17, debug-сборка `0a0fcc4e`, простой интерфейс, «Авто» над подпиской из трёх локальных серверов
shadowsocks (Docker), журнал `files/core.log` уровня info.
1. Подключиться, дождаться «Защищено».
2. Сделать недоступными все три сервера при живой сети (остановить контейнеры / оставить порт, который принимает TCP и молчит).
3. Наблюдать журнал. Фактически:
   ```
   00:33:00 [Warning] [Auto selector] Every running profile stopped working — rebuilding from the next best candidates.
   00:33:00 [Auto selector] Measuring 1 not-yet-tested profiles...
   00:33:02 [Auto selector] Ranked 3 profiles.
   00:33:02 ServiceStopTrace … restart=true state=Connected …
   00:33:02 VpnLifecycleTrace stage=tun-close success
   00:33:06 [Auto selector] Running the best 3 of 3 ranked profiles.
   00:34:01 [Warning] [Auto selector] Every running profile stopped working — rebuilding …
   00:34:01 [Auto selector] Measuring 3 not-yet-tested profiles...
   00:34:05 ServiceStopTrace … restart=true …  tun-close …
   00:34:14 [Auto selector] Running the best 3 of 3 ranked profiles.
   ```
   Оба раза ядро пересобрано из тех же 3 из 3 серверов; ни один не стал рабочим. Наблюдение длилось ~2 минуты.
4. Что ещё стоит проверить длинным прогоном (15–20 мин): растут ли интервалы 60 → 120 → 240 с. Есть основание
   сомневаться: после перезапуска участники ядра на время числятся `untested`, это считается «годным» (`:532`) и сбрасывает
   паузу в 0 (`:550` `if (usable > 0) rebuildBackoffS = 0`). Если так, цикл идёт не реже раза в ~(время отбраковки + 20 с), а
   не с нарастающей паузой. Интервал 61 с между первыми двумя пересборками совместим с обоими вариантами.

## What Changes
1. (рекомендуется) В `onExhausted` для обычного (не «за цепочкой») автовыбора не перезапускать ядро, если пересборка не может
   дать другой набор: `plan.pool.size <= plan.build.size` (то же правило, что в `demoteLastBuilt`), либо после
   переранжирования новая сборка совпадает с работающей. Вместо перезапуска — `AutoSelectorCore.recheck()` (уже есть,
   `AutoSelectorCore.kt:26`) и одна строка в статусе/уведомлении «Все серверы недоступны».
2. Сбрасывать паузу пересборки только по участнику, который действительно ответил (`ok`/`degraded`), а не по `untested`.
3. Не перетестировать при каждом эпизоде участников, чей провал свежее текущей паузы.

Проверка: тот же сценарий 20 минут — 0 строк `ServiceStopTrace restart=true` и 0 прямых соединений, пока набор серверов не
меняется; при оживлении сервера ядро переходит на него само (строка «Running …» без перезапуска либо обычное переключение
участника).

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `auto-selector`: «Automatic node selection» — добавить сценарий «все кандидаты не отвечают при живой сети»: сервис не
  перезапускает соединение, если пересборка не может дать других кандидатов, и сообщает о недоступности через «Selector state
  visibility».

## Impact
- **Код:** `bg/autoselector/AutoSelectorRuntime.kt` (`onExhausted`, `rebuild`, `onSample`), возможно
  `bg/autoselector/AutoSelectorProfiles.kt` (общий помощник «может ли пересборка что-то изменить»).
- **Upstream:** **патч в upstream** — файлов автовыбора нет в `TOUCH_POINTS`; новая точка правки ради этого нецелесообразна,
  изменение полезно и upstream.
- **Ядро throne, сборка, инструменты:** ядро не меняется; используется существующее действие `recheck`. Предположение о
  поведении ядра — участники после старта временно `untested` (пункт 2) — проверяется длинным прогоном.
- **Риски:** если ядро «залипает» в состоянии, из которого выходит только пересозданием, `recheck` окажется слабее
  перезапуска; компромисс — разрешить перезапуск не чаще раза в 10–30 минут. Desktop (на котором основан алгоритм) делает
  перезапуск — это осознанное расхождение для мобильного сценария. Для пулов больше лимита сборки поведение не меняется.
- **Проверка исправления:** сценарий выше; JVM-тест правила «пересборка бесполезна» на плане с `pool.size <= build.size`.
